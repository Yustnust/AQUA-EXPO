## 一、🔴 P0 - 致命 BUG

### BUG #E1：`FC19` 急停解除路径几乎所有动作失效——系统永远卡在 S_ERROR

**严重度**：🔴 P0 致命
**影响范围**：所有"急停解除+系统复位按钮"路径

**位置**：`FC19_State_Error.stl` L45-67

```stl
LDN    I1.1                        ; 急停已释放
A      I0.3                        ; 系统复位按钮按下
EU                                 ; 上升沿
R      V300.4, 1                   ; 清急停锁存
R      V300.0, 4                   ; ⚠️ 此后所有指令栈空失效
R      V1.6, 1
R      V1.7, 1
FILL   0, VW260, 8                 ; 清阀诊断子状态
R      T50, 6                      ; 清阀诊断计时器
MOVW   0, VW2                      ; 转S0
MOVW   0, VW6                      ; 清报警码
R      V0.0, 1                     ; 清启动命令
R      Q0.7, 1                     ; 关报警声音
JMP    2
```

**栈追踪**：
```
LDN    I1.1       → 栈:[NOT I1.1]                    (深 1)
A      I0.3       → 栈:[NOT I1.1 AND I0.3]          (深 1)
EU                → 栈:[(NOT I1.1 AND I0.3)↑]        (深 1, 上升沿脉冲)
R      V300.4, 1  ; 消耗栈顶，V300.4=0              (深 0)
R      V300.0, 4  ; 栈空，⚠️ 不执行!
R      V1.6, 1    ; 栈空，⚠️ 不执行!
R      V1.7, 1    ; 栈空，⚠️ 不执行!
FILL   0, VW260, 8; 栈空，⚠️ 不执行!
R      T50, 6     ; 栈空，⚠️ 不执行!
MOVW   0, VW2     ; 栈空，⚠️ 不执行!
MOVW   0, VW6     ; 栈空，⚠️ 不执行!
R      V0.0, 1    ; 栈空，⚠️ 不执行!
R      Q0.7, 1    ; 栈空，⚠️ 不执行!
JMP    2          ; 不消耗栈，跳走
```

**后果（严重）**：
- **唯一执行的就是 `R V300.4, 1`**——急停锁存清除
- **VW2 永远不变成 0**——系统**永远卡在 S_ERROR**
- **VW6 永远不清零**——报警码永久显示
- **V1.6/V1.7 不清空**——缸状态错误
- **VW260 不清**——FC11/FC15/FC17 的 `AW= VW260, 0` 前置条件失败（P0 BUG #6 的修复点！）
- **Q0.7 报警声音永远响**——消音失效

**实际场景**：
- 操作员急停后，按下系统复位按钮 → **急停锁存清除，但系统不返回 S0**
- 操作员看到的是"急停状态指示消失但系统仍报 S_ERROR"
- 重新上电仍然卡 S_ERROR

**修复方法**：

**方案 A（推荐）：每条独立 LD**
```stl
LDN    I1.1
A      I0.3
EU
R      V300.4, 1

LD     V_reset_pulse        ; 用 M/V 区保存 EU 结果
R      V300.0, 4
R      V1.6, 1
R      V1.7, 1
FILL   0, VW260, 8
R      T50, 6
MOVW   0, VW2
MOVW   0, VW6
R      V0.0, 1
R      Q0.7, 1
```

**方案 B：用 LPS 保存 EU 结果**
```stl
LDN    I1.1
A      I0.3
EU
LPS                         ; 保存 EU 结果到第 2 层
R      V300.4, 1
R      V300.0, 4
R      V1.6, 1
R      V1.7, 1
FILL   0, VW260, 8
R      T50, 6
MOVW   0, VW2
MOVW   0, VW6
R      V0.0, 1
R      Q0.7, 1
LPP
JMP    2
```

### BUG #E2：`FC3` 优先级链覆盖了 `FC2` 的急停报警码赋值——急停显示为漫溢级编码

**严重度**：🔴 P0 致命
**影响范围**：所有急停报警的显示与处理

**位置**：
- `FC2_EStopHandling.stl` L46-52
- `FC3_AlarmHandling.stl` L30-31、L51-52

**OB1 调度顺序**：`FC2 → FC4 → FC3 → ...`

```stl
// FC2 NETWORK 1
LD     V300.5
MOVW   99, VW6                    ; 继电器故障 → VW6=99
JMP    1
LD     V300.4
AN     V300.5
MOVW   10, VW6                    ; 急停 → VW6=10  ⚠️ 会被 FC3 覆盖
LBL    1
```

```stl
// FC3 NETWORK 1
LD     SM0.0
MOVW   0, VW6                    ; ⚠️ 每周期都把 VW6 清 0！
LD     V300.5
MOVW   99, VW6
...
LDW=   VW6, 0                    ; 漫溢级检查
A      V300.0
MOVW   10, VW6
LDW=   VW6, 0
A      V300.1
MOVW   11, VW6
LDW=   VW6, 0
A      V300.2
MOVW   12, VW6
LDW=   VW6, 0
A      V300.3
MOVW   13, VW6
LDW=   VW6, 0
A      V300.4                      ; ⚠️ V300.4（急停）也在漫溢级检查中
MOVW   14, VW6                    ; 急停 → VW6=14（与 FC2 冲突）
```

**问题分析**：

1. **调度顺序**：OB1 先调 FC2，再调 FC3
2. **FC2 写 VW6=10**（急停）
3. **FC3 第一件事是 MOVW 0, VW6**——**把 FC2 写的 10 清 0！**
4. 然后 FC3 逐级检查，V300.4=1 → `LDW= VW6, 0; A V300.4; MOVW 14, VW6`——**VW6 = 14**
5. **最终 VW6 = 14（漫溢级编码），而不是 10（急停级编码）**

**后果**：
- HMI 显示"急停"时看到的报警码是 **14**，不是设计文档定义的 **10**
- 报警码字典里 14 = "急停锁存"，10 = "急停触发"——但 **FC3 把 14 标记为漫溢级**，**10 没有编码**（FC2 写 10 后被覆盖）
- 操作员看到的是漫溢级处理（强制人工确认）——**这个倒是对了**，但编码混乱

**修复方案**：

**方案 A（推荐）：删除 FC3 的 V300.4 处理**
```stl
// FC3 NETWORK 1 删除 V300.4 段：
//  LDW= VW6, 0
//  A    V300.4
//  MOVW 14, VW6

// 由 FC2 单独处理 V300.4 → VW6=10
// FC3 不再重复处理
```

**方案 B：FC2 不写 VW6**
```stl
// FC2 NETWORK 1
LD     V300.5
S      V300.5_latch     ; 用 V 区保存继电器故障
LD     V300.4
S      V300.4_latch     ; 用 V 区保存急停锁存
// 不再 MOVW VW6，由 FC3 统一编码
```

## 二、🟠 P1 - 严重 BUG

### BUG #E3：FC3 报警确认路径的"门控修复"栈管理 OK，但 `R V0.3, 1` 与 `CALL AlarmReset_Common` 紧邻可能产生时序问题

**严重度**：🟠 P1 严重（隐性 BUG，依赖时序）

**位置**：`FC3_AlarmHandling.stl` L184-208

```stl
LD     V0.3
EU
=      V60.5                         ; 缓存 EU 结果
LDN    V60.5
JMP    40                            ; 无上升沿跳过
LD     V60.5

S      V1.3, 1                       ; 报警确认握手
R      V0.3, 1                       ; 清确认命令
...
CALL   AlarmReset_Common             ; 调用公共复位
LBL    40
```

**问题**：
- `R V0.3, 1` 在 `CALL AlarmReset_Common` 之前
- 如果 `AlarmReset_Common` 内部某些复位条件依赖 V0.3 状态——**V0.3 已被清，无法使用**
- 当前 `AlarmReset_Common` 不读 V0.3，所以**实际无影响**
- 但**架构层面有耦合**——如果未来给 `AlarmReset_Common` 加 V0.3 门控，会引入难发现的 BUG

**修复建议**：把 `R V0.3, 1` 移到 `CALL AlarmReset_Common` 之后。

### BUG #E4：`FC4` 与 `FC40` 对 V303.6（周期超时报警位）的 S/R 冲突

**严重度**：🟠 P1 严重

**位置**：
- `FC4_ModbusPolling.stl` L100、L232：`R V303.6, 1`
- `FC40_RhythmCorrection.stl` L56、L136：`S V303.6, 1`

**问题**：
- FC4 第 100 行：流量计通讯成功 → R V303.6
- FC4 第 232 行：连续失败 < 5 次（VW294 < 5）→ R V303.6
- FC40 第 56 行：T_cycle ≤ 0（参数过激进）→ S V303.6
- FC40 第 136 行：T46/T48 计时完成 + 不在 S7 → S V303.6

**OB1 调度顺序**：`FC0 → FC2 → FC4 → FC3 → FC22 → FC40 → FC1`

**实际执行**：
1. FC4 通讯成功 → R V303.6 = 0
2. FC40 计时完成 → S V303.6 = 1
3. **最终 V303.6 = 1**（FC40 后置位）

但**如果通讯失败**：
1. FC4 通讯失败 → VW294++
2. 连续失败 < 5 次 → R V303.6（清掉 FC40 之前置位的 V303.6）
3. FC40 → S V303.6
4. **最终 V303.6 = 1**（FC40 后置位）

**注释错位**：
- FC4 L222 注释"软件滤波 合并 (原 34/35/36)"——属于历史版本
- FC4 L230 注释"V303.6 软件滤波:连续失败<5次时不报警"——**但 V303.6 不是"通讯失败"位,是"周期超时"位!**

**实际语义混乱**：FC4 注释说"V303.6 软件滤波"，但实际 FC40 用 V303.6 表示"周期超时"。这是 v2.2 复用 V303.6（原流量开关瞬时异常位）造成的命名混乱。

**修复方案**：

**方案 A：FC4 不清 V303.6**
```stl
// FC4 NETWORK 全部删除 R V303.6, 1
// V303.6 仅由 FC40 管理
```

**方案 B：FC4 清的是别的位（注释修正）**
```stl
// FC4 第 100 行和 232 行实际上是清另一个位（可能是 V303.5？V303.4？）
// 需要核对实际语义
```

### BUG #E5：FC2 急停触发条件缺乏延时确认——电磁干扰尖峰会永久锁存 S_ERROR

**严重度**：🟠 P1 严重

**位置**：`FC2_EStopHandling.stl` L24-29

```stl
LD     I1.1
EU
AN     SM0.1                      ; 首次扫描周期不触发(调试临时)
S      V300.4, 1
```

**问题**：
- `AN SM0.1`（AND NOT SM0.1）只能挡住 PLC 冷启动后**第一周期**的尖峰
- 冷启动第二周期开始后 SM0.1 = OFF，急停保护失效
- 任何运行时 I1.1 电磁干扰尖峰（哪怕只 1 个扫描周期）都会被 EU 捕获，永久锁存 V300.4
- 注释说"调试临时"——**说明这个保护不充分**，应该用 TON 延时确认

**修复方案**：
```stl
NETWORK 1
// 急停信号延时确认(100ms 内持续触发才认定为真)
LD     I1.1
TON    T36, 1000                   ; 100ms 延时（PT=1000 × 100ms=100s?）

NETWORK 2
// 延时到达后置位急停锁存
LD     T36
EU
AN     SM0.1
S      V300.4, 1
MOVW   99, VW2
```

**注意**：TON 的 PT 单位是 100ms，所以 PT=1 表示 100ms——需要根据实际物理动作时间设置。

### BUG #E6：FC19 急停解除路径缺 I1.1 持续确认——可能误清急停锁存

**严重度**：🟠 P1 严重

**位置**：`FC19_State_Error.stl` L45-47

```stl
LDN    I1.1                        ; 急停已释放
A      I0.3                        ; 系统复位按钮按下
EU                                 ; 上升沿(按下瞬间)
```

**问题**：
- `LDN I1.1` 是当前周期的 I1.1 状态（OFF=急停未触发）
- `A I0.3 EU` 是 I0.3 上升沿
- **如果操作员按住 I0.3 的同时又按下了急停按钮**（极不合理但可能发生）：
  - I0.3 ON + I1.1 OFF → 条件满足 → R V300.4 清急停锁存
  - 但此时急停按钮实际是按下的（I1.1 应该是 ON——等等，注释说 "I1.1 常开 NO, OFF=正常, ON=急停触发"）
  - **如果操作员松开急停（I1.1=OFF）后立即按系统复位（I0.3 上升沿）—— OK 没问题**
- **但如果急停按钮接触不良**（按下后 I1.1 偶发 OFF 抖动），操作员按系统复位时刚好 I1.1=OFF，就会误清急停锁存

**修复方案**：I1.1 状态需要持续 N 秒确认（如 200ms TON）：
```stl
// 在 FC2 或 FC19 中增加：
LD     I1.1
TON    T37, 2000                   ; 2 秒延时确认急停已稳定释放
```

### BUG #E7：FC19 继电器故障高权限确认路径未限定安全继电器实际反馈状态

**严重度**：🟠 P1 严重

**位置**：`FC19_State_Error.stl` L74-79

```stl
LBL    1
LD     V0.7                        ; HMI高权限确认命令
EU                                 ; 上升沿
A      I1.2                        ; 且安全继电器反馈确实正常(已检修)
R      V300.5, 1                   ; 清除继电器故障报警
R      V0.7, 1                     ; 清确认命令
```

**问题**：
- `A I1.2` 表示"安全继电器反馈=ON（即动力回路已接通，I1.2=1）"
- **但继电器故障的实际定义是 "I1.2=1 但 V300.5 已置位"**——即"动力回路未断开（I1.2=1），但急停已触发"
- 修复后要求"动力回路已接通"（I1.2=1）——这意味着**操作员必须先把所有急停按钮释放**，让动力回路重新接通
- 但如果现场有多个急停按钮，**其中一个仍按下**（但 I1.1 PLC 输入可能没接），动力回路可能仍然断开——I1.2=0——**确认会被 A I1.2 拒绝**
- 这是**安全设计**：要求操作员真正确保所有急停已释放
- **但**：I1.2 的"ON=动力回路已接通"语义**要求安全继电器重新上电**——这一步需要操作员在硬件层面操作（重新合闸）——**流程断裂**

**修复建议**：
- 在 HMI 上提示"继电器故障清除需要：① 所有急停按钮释放 ② 现场重新上电 ③ HMI 高权限确认"
- 或加一个"继电器已重新上电"按钮（DI 输入），与 V0.7 联动

### BUG #E8：FC3 自动恢复路径在 V200.0 模式下重置 V301.4/V301.5 等一般故障——但文档说"高优先级不受影响"，缺少保护

**严重度**：🟠 P1 严重（设计漏洞）

**位置**：`FC3_AlarmHandling.stl` L217-235 + `FC3A_AlarmReset_Common.stl` 整个文件

**问题**：
- FC3 NETWORK 5（自动恢复）调用 `AlarmReset_Common`
- `AlarmReset_Common` 重置 V301.x/V302.x/V303.x/V303.4 等
- **设计文档 §8.1 说"高优先级（漫溢/节奏滞后/继电器故障）不受 M_AlarmAckMode 影响"**
- 但 FC3 NETWORK 5 没有检查"当前 VW6 是否是高优先级"——只要 V200.0=0（自动模式），**所有 V301/V302/V303 都被重置**
- **如果 V301.x（阀类故障）置位时操作员已经把 S_ERROR 触发了**（VW2=99），FC3 NETWORK 5 会先检查 VW2=99 跳过——但这只是 NETWORK 5 跳过，NETWORK 4 的 V0.3 路径仍会重置

**修复建议**：
```stl
// FC3 NETWORK 4 报警确认前加保护:
LDW=   VW2, 99
JMP    40                            ; S_ERROR 态跳过所有自动/手动复位

LD     V0.3
EU
=      V60.5
LDN    V60.5
JMP    40
LD     V60.5

; ... 确认处理 ...
```

## 三、🟡 P2 - 中等 BUG

### BUG #E9：FC3 优先级链"短路"逻辑依赖 MOVW 栈顶 FALSE 不执行——但 S7-200 SMART 的某些版本会强制执行 MOVW

**严重度**：🟡 P2 中等（取决于固件版本）

**位置**：`FC3_AlarmHandling.stl` L37-128

**问题**：
- 优先级链用了 `LDW= VW6, 0; A Vxxxx; MOVW xx, VW6`
- 设计意图：MOVW 只在栈顶=TRUE 时执行
- S7-200 SMART 大多数固件版本下 MOVW 在栈顶=FALSE 时**不执行**，符合预期
- 但某些早期固件版本（V1.0 之前）MOVW 会**无条件执行**——这会让优先级链失效，所有报警码都被覆盖为最后一个 MOVW 值
- **风险**：取决于现场 PLC 固件版本

**修复建议**：改用更安全的模式：
```stl
// 用 JMP/LBL 替代短路逻辑
NETWORK 1
LD     V300.5
JMP    99
MOVW   99, VW6
LBL    99
NETWORK 2
...
```

### BUG #E10：FC2 NETWORK 1 第 41 行 `MOVB 0, QB0` 后第 42 行 `S Q0.7, 1`——但 Q0.7 在 QB0 范围内

**严重度**：🟡 P2 中等

**位置**：`FC2_EStopHandling.stl` L40-42

```stl
LD     V300.4
MOVB   0, QB0                     ; 清 Q0.0~Q0.7（包括 Q0.7）
S      Q0.7, 1                     ; S Q0.7（报警声音开）
```

**问题**：
- `MOVB 0, QB0` 清 Q0.0~Q0.7，包括 Q0.7（声音）
- 紧接着 `S Q0.7, 1` 置 Q0.7
- 这两步**互相覆盖**——但因为是顺序执行，最终 Q0.7=1（声音开）
- **无功能性问题**，但**写得很别扭**——可以拆分为：
  ```stl
  MOVB 0, QB0
  S    Q0.7, 1
  ```
- 实际上 `MOVB 0, QB0` + `S Q0.7, 1` 的效果和 `MOVB 1, QB0` 不一样（后者会同时置 Q0.0~Q0.7）

**修复建议**：注释说明为什么需要两步，或者拆分为：
```stl
LD     V300.4
MOVB   0, QB0                     ; 清 Q0.0~Q0.6（泵/阀/NC阀）
S      Q0.7, 1                     ; Q0.7 = 1（报警声音）
```

注意 QB0 是字节(8 位,Q0.0~Q0.7)，**没有更好的写法**。这只是代码可读性问题。

### BUG #E12：FC3A V302.0/V302.5 复位条件过于宽松——可被"假性复位"

**严重度**：🟡 P2 中等

**位置**：`FC3A_AlarmReset_Common.stl` L39-43、L61-65

```stl
LD     V302.0
LD     I0.1                  ; 流量开关B=ON
O      I0.6                  ; 或液位计A-低位=ON
ALD
R      V302.0, 1
```

**问题**：
- 复位条件：`V302.0=1 AND (流量开关B=ON OR 液位计A-低位=ON)`
- 设计文档 §6.1 阀B四态诊断：
  - 状态 4（流量开关 OFF + 液位低位 OFF）→ V302.0 置位
- 复位条件应该：离开状态 4
- 当前条件：液位低位 ON 即可复位——**但液位低位 ON 不代表阀B 故障已排除**

**实际场景**：
- 阀B 流量开关 B 卡死（一直 OFF）→ V302.0 置位
- 上缸液位降到位（I0.6 ON）→ V302.0 被错误清除
- 操作员看到 V302.0 消失，以为故障已解决——**但流量开关 B 仍卡死**

**修复建议**：复位条件应该要求流量开关 B 物理恢复：
```stl
LD     V302.0
A      I0.1                  ; 流量开关B必须ON（已恢复）
R      V302.0, 1
```

但这要求 S4 转移期间流量开关 B 必然恢复——**事实上 S4 转移是流量开关 B 应该 ON 的阶段**，所以这个条件合理。

**更稳妥的方案**：V302.0 必须由 V0.3 人工确认清除，不参与自动恢复——与"状态 4 是设备故障"的语义一致。

### BUG #E15：FC19 自动解锁路径的 `AN I1.1` 注释说"急停按钮已释放"——但 I1.1 接的是 NO 常开触点

**严重度**：🟡 P2 中等（注释/语义）

**位置**：`FC19_State_Error.stl` L98

```stl
AN     I1.1                 // 急停按钮已释放(NO触点OFF)
```

**问题**：
- 注释说 "NO 触点 OFF"——但设计文档 §9.1 明确"急停按钮本身必须为常闭型触点"
- PLC DI 接的是**急停按钮的第二组独立常闭触点**
- **但 FC19 文件头注释说"急停反馈(常开 NO, OFF=正常, ON=急停触发) v1.3 改 NO 接法"**——**自相矛盾**
- 实际 v10.2 文档说 "I1.2=1 表示动力回路已接通"——这意味着 I1.1 是接 NO 触点（按下=I1.1=ON）

**实际接法**：v10.2 文档 §9.3 写"I1.1 恢复 ON（触点重新闭合）后，状态机不自动恢复"——**I1.1=ON=急停释放**——所以 I1.1 接的是**常闭触点的 NO 端**（按下断开=OFF，释放闭合=ON），是反逻辑的常开接法。

**代码注释正确**（I1.1=OFF=急停触发，I1.1=ON=急停释放），但**设计文档 §9.1 的"常闭触点"描述容易引起混淆**。

**修复建议**：在文档中明确"I1.1 PLC 输入信号=OFF 表示急停已触发，=ON 表示急停已释放（常闭触点的 NO 端接法）"。

### BUG #E16：FC3 第 161-169 行的消音处理栈管理 OK，但 `R V0.4, 1` 与 HMI 握手可能冲突

**严重度**：🟡 P2 中等

**位置**：`FC3_AlarmHandling.stl` L161-169

```stl
LD     I0.4
EU
LD     V0.4
EU
OLD                                 ; 两者任一上升沿
R      Q0.7, 1                       ; 关声音
S      M11.1, 1                      ; 置消音标志(新报警时清)
S      V1.4, 1                       ; STA_MuteDone握手
R      V0.4, 1                       ; 清HMI消音命令
```

**问题**：
- `R V0.4, 1` 在 OLD 之后，但栈顶是 OLD 的结果——`R V0.4` 消耗 OLD 结果，**剩余栈空**
- 实际上 OLD 压栈深度只有 1，所以 R 后栈空——`S M11.1, S V1.4, R V0.4` 都依赖栈顶，会执行成功
- 但栈管理很别扭

**实际追踪**：
```
LD I0.4 → 栈:[I0.4]
EU      → 栈:[I0.4↑]
LD V0.4 → 栈:[V0.4, I0.4↑]
EU      → 栈:[V0.4↑, I0.4↑]
OLD     → 栈:[(V0.4↑ OR I0.4↑)]   (深 1)
R Q0.7  → 消耗栈顶; 栈:[]
S M11.1 → 栈空，不执行!  ⚠️
S V1.4  → 不执行
R V0.4  → 不执行
```

**等等**——这段**真的有栈管理问题**！让我再仔细追一遍。

实际上 OLD 的语义是 OR with LD：把两个值做 OR，结果压栈。所以：
```
LD I0.4     → 栈:[I0.4]                   (深 1)
EU          → 栈:[I0.4↑]                  (深 1)
LD V0.4     → 栈:[V0.4, I0.4↑]            (深 2)
EU          → 栈:[V0.4↑, I0.4↑]           (深 2)
OLD         → 把栈顶和次栈顶做 OR，弹出次栈顶，结果压栈:栈:[(V0.4↑ OR I0.4↑)]   (深 1)
R Q0.7, 1   → 消耗栈顶; 栈:[]
S M11.1, 1  → 栈空，⚠️ 不执行!
S V1.4, 1   → 不执行
R V0.4, 1   → 不执行
```

**确认：S M11.1/S V1.4/R V0.4 都因为栈空不执行！**

后果：
- **M11.1 永远不被置位**——下次报警时无法消音
- **V1.4 消音握手永远不发**——HMI 不知道 PLC 已消音
- **V0.4 不清零**——HMI 命令位残留

但**消音的实际行为**：R Q0.7, 1 执行成功——声音确实关了。但下次新报警时 M11.1 仍为 0（从未置位）——声音会重鸣，但**M11.1 永远没被清过**——下次消音动作依然走同样的死路径——**消音永远是单次有效，新报警永远重鸣**。

**修复方案**：
```stl
LD     I0.4
EU
LD     V0.4
EU
OLD
R      Q0.7, 1
S      M11.1, 1
S      V1.4, 1
R      V0.4, 1

// 用 LD I0.4_OR_V0.4 缓存 OLD 结果（用 M/V 位）
```

## 五、FC2/FC3/FC19 与 OB1 调度顺序分析

OB1 调用顺序：
```
NETWORK 1: SysInit (SM0.1)
NETWORK 2: EStopHandling (FC2)            ← 急停，最高优先级
NETWORK 3: 停止命令 (V0.2)
NETWORK 4: ModbusPolling (FC4)
NETWORK 5: AlarmHandling (FC3)            ← 报警
NETWORK 6: RTC_Sync (FC22)
NETWORK 7: RhythmCorrection (FC40)        ← 双倒计时器
NETWORK 8: StateDispatcher (FC1)
NETWORK 9: 上缸子流程调度 (FC11/FC1A)
...
```

**关键时序**：
1. **FC2 写 VW6=10/99 → FC3 清 VW6=0 → FC3 重算 VW6**——**FC2 的报警码被覆盖**（BUG #E2）
2. **FC4 R V303.6 → FC40 S V303.6**——**正常时 FC40 后置位生效**（BUG #E4）
3. **FC3 清 M11.1 → FC19 S M11.x**——消音状态可能错乱

**建议**：
- FC2 不再写 VW6（只置 V300.4/V300.5，由 FC3 统一编码）
- FC4 不再操作 V303.6（仅由 FC40 管理）
- FC3/FC19 消音标志统一管理

## 八、整体建议

1. **BUG #E1 是最致命的**——系统复位路径**几乎所有动作失效**，操作员按下复位按钮后系统仍卡 S_ERROR。建议立即修复。
2. **BUG #E2 是报警码字典错乱**——FC2 和 FC3 都写 VW6，必须立即统一。建议 FC2 只置位（V300.4/V300.5），由 FC3 统一编码。
3. **BUG #E5/#E6 是安全相关**——急停触发/解除都需要延时确认，避免电磁干扰导致误锁存或误清除。建议加 TON 延时。
4. **BUG #E4/V303.6 S/R 冲突**是架构问题——FC4 不应清 V303.6。建议 FC4 只清 V303.4（注射泵报警位），不动 V303.6。
5. **BUG #E16 消音栈消耗**——实际消音只关声音，但**握手信号不发**，HMI 不知道已消音。建议立即修复。
