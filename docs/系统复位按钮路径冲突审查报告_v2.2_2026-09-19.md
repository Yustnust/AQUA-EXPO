# 系统复位按钮 (I0.3) 路径冲突审查报告

> **审查日期**:2026-09-19
> **审查人**:PLC 代码审查助手
> **审查对象**:`feature/v2.2-doc-revisions` 分支 I0.3 系统复位按钮相关代码
> **核心问题**:一个系统复位按钮 (I0.3) 实现了两个不同的复位流程(§4.3 S7 复位 + §9.3 S_ERROR 复位),**是否会走错路径?**

> **审查结论**:**🟢 不会走错路径,但有 3 处风险点需要注意**
>
> 总体上 FC18 和 FC19 的复位路径通过 **VW2 当前状态** 自然互斥——同一周期只可能进入其中一个。逻辑上不会走错。但仍有 3 处风险:状态切换瞬间、FC19 自动解锁路径、V300.4 未清除的极端场景。

---

## 一、问题描述

### 1.1 用户提出的疑问

I0.3 是**物理系统复位按钮**(就地面板),**两个不同的流程都在监听它**:

| 流程 | 触发条件 | 触发器 | 复位动作 | 来源 |
|---|---|---|---|---|
| **§4.3 S7 复位** | VW2=8(实验结束) | I0.3 上升沿 | 清 M10.6/V1.0/VD364/440/372,VW2=0 | FC18 L35-47 |
| **§9.3 S_ERROR 复位** | VW2=99(故障锁定) | I0.3 上升沿 | 清 V300.4/V300.0~3/V1.6/V1.7,清 VB260-275/T50-T55,VW2=0,VW6=0,V0.0,R Q0.7 | FC19 L45-67 |

### 1.2 核心疑问

操作员按下 I0.3 时,**PLC 怎么知道该走 FC18 还是 FC19**?会不会:
- 该走 FC18 却走了 FC19(或反过来)?
- 两条路径的复位动作会互相干扰?
- 在某个边界条件下,按 I0.3 既走了 FC18 又走了 FC19?

---

## 二、答案先说:为什么不会走错

### 2.1 核心机制:**OB1 调用顺序保证同一周期只可能命中一个**

OB1 在 NETWORK 11 调用 `StateDispatcher`(FC1),FC1 通过 JMP/LBL 表根据 **VW2 当前值** 分发:

```stl
// FC1_StateDispatcher.stl L25-50
LDW=  VW2, 8     JMP 5     // → LBL 5: CALL State_S7_End (FC18)
LDW=  VW2, 99    JMP 6     // → LBL 6: CALL State_Error (FC19)
... 其他状态值
```

**关键事实**:**同一周期,VW2 只能是 8 或 99 中的一个值**(除非刚刚被改写)——FC1 一次只命中一个 JMP,LBL 一次只进入一个分支。

**所以**:**I0.3 按下后,FC18 和 FC19 不会在同一周期同时执行复位动作**。

### 2.2 路径分支图

```
[操作员按 I0.3]
      │
      ▼
[OB1 NETWORK 11 → CALL StateDispatcher (FC1)]
      │
      ▼
[FC1: 读 VW2 → 跳到对应分支]
      │
      ├── VW2=8  → CALL FC18_State_S7_End → 检查 I1.1=I0.3↑ → 执行 S7 复位动作
      │
      ├── VW2=99 → CALL FC19_State_Error  → 检查 V300.5 → 检查 I1.1=I0.3↑ → 执行 S_ERROR 复位动作
      │
      └── 其他 VW2 值 → CALL FC10 (S0) → FC10 不监听 I0.3 → 无动作
```

### 2.3 验证表

| 当前 VW2 | 调用哪个 FC | I0.3 按下后执行哪些动作? |
|---|---|---|
| 0 (S0) | FC10_StartupInitial | **无**——FC10 不监听 I0.3 |
| 1 (S1) | FC11 | **无**——FC11 不监听 I0.3 |
| 2 (S2) | FC1A | **无** |
| 5 (S4) | FC15 | **无** |
| 6 (S5) | FC16 | **无** |
| 7 (S6) | FC17 | **无** |
| **8 (S7)** | **FC18** | ✅ 执行 §4.3 S7 复位(M10.6/V1.0/VD364/440/372,VW2=0) |
| **99 (S_ERROR)** | **FC19** | ✅ 执行 §9.3 S_ERROR 复位(V300.4/V300.0~3/V1.6/V1.7,清 VB260-275/T50-T55,VW2=0,VW6=0,V0.0,R Q0.7) |

## 三、不会走错路径,但有 3 处风险点

### 风险 #1:状态切换瞬间 —— 临界条件 ⚠️

**场景描述**:
- T1 时刻:VW2=8(在 S7),FC18 正在运行
- T2 时刻(同周期):**其他 FC 把 VW2 改成 99**(虽然不常见)
- T3 时刻:操作员按下 I0.3

**问题**:**如果 I0.3 上升沿恰好在 VW2=8→99 的切换周期内**——PLC 内部对 VW2 是字节级读写,**S7-200 SMART 是单任务系统**(没有真正的并行),所以**实际不会发生**——但理论值得注意。

**实际代码保护**:
- FC18 L35-47:`LDN I1.1; A I0.3; EU; ...; MOVW 0, VW2`——执行后 VW2=0,下一周期 FC1 分发到 FC10
- FC19 L45-67:同样执行后 VW2=0,下一周期 FC1 分发到 FC10

**结论**:**不会走错**——但**VW2 切换瞬间的"按下 I0.3"事件可能被 EU 漏检**(EU 是边沿检测,需要稳定 1 个周期)。

### 风险 #2:FC19 自动解锁路径 —— 双路径触发 ⚠️

**重要发现**:**FC19 在 NETWORK 4 还有一个"自动解锁"逻辑**(L94-108),**与 I0.3 路径完全独立**:

```stl
// FC19 L94-108
LDW=  VW2, 99                     // 确实锁在 S_ERROR
AW=   VW6, 0                      // 报警系统已清零
AN    V300.4                      // 不是急停锁存
AN    V300.5                      // 不是继电器故障
AN    I1.1                        // 急停按钮已释放
AN    V303.5                      // 不是 RTC 丢失
FILL 0, VW260, 8
R    T50, 6
MOVW 0, VW2                       // 自动回 S0
MOVW 0, VW6
R    Q0.7, 1
```

**触发条件**:
- VW2=99(锁在 S_ERROR)
- **VW6=0(报警系统已清零)**——这是关键
- V300.4=0(无急停锁存)
- V300.5=0(无继电器故障)
- I1.1=OFF(急停已释放)
- V303.5=0(无 RTC 报警)

**风险场景**:
- S_ERROR 状态 + 所有报警已被自动清除 + 急停已释放
- **此时 PLC 自动回 S0,不需要按 I0.3**
- **如果此时操作员按 I0.3**——FC19 NETWORK 2 (V300.5) 不跳转,NETWORK 3 系统复位条件命中,执行 NETWORK 3 的复位动作(同时 NETWORK 4 也命中自动解锁)

**后果**:
- NETWORK 3 复位动作:清 V300.4/V300.0~3/V1.6/V1.7、清 VB260-275/T50-T55、VW2=0、VW6=0、V0.0、R Q0.7
- NETWORK 4 自动解锁动作:FILL VB260-275、R T50-T55、VW2=0、VW6=0、R Q0.7
- **JMP 2 在 NETWORK 3 末尾**——NETWORK 4 **不会执行**(被 JMP 跳过)

**结论**:**不会重复执行,但 NETWOEK 4 实际上被 JMP 2 跳过了**——这是设计意图(优先响应系统复位按钮)。

**但有一个隐患**:**如果 NETWORK 3 复位动作链栈消耗失效,LPS 后 R/V300.x 等不执行,而 NETWORK 4 自动解锁的 FILL/R T50 也需要栈顶……** ——实际上 NETWORK 4 也可能失效。

### 风险 #3:V300.4(V300.5)清除不彻底的极端场景 🔴

**场景描述**:
- VW2=99,V300.4=1(急停锁存)
- V300.5=0(无继电器故障)
- 操作员:① 释放急停 → I1.1=OFF;② 按 I0.3
- FC19 NETWORK 2 不跳转 → 进入 NETWORK 3
- 复位动作执行:**R V300.4** 清急停锁存 ✓

**正确路径**——但有一个**风险点**:

```stl
// FC19 L45-66 实际写法
LDN   I1.1                        // 急停已释放
A     I0.3                        // 系统复位按钮
EU                                // 上升沿
R    V300.4, 1                    // 清急停锁存
R    V300.0, 4                    // 清漫溢级
R    V1.6, 1                      // 上缸=空
R    V1.7, 1                      // 下缸=空
FILL 0, VW260, 8                  // 清 VB260-275
R    T50, 6                       // 清 T50~T55
MOVW 0, VW2                       // 回 S0
MOVW 0, VW6                       // 清报警码
R    V0.0, 1                      // 清启动命令残留
R    Q0.7, 1                      // 关报警声音
JMP  2                            // → FC19 结束
```

**栈消耗问题**(根据之前的代码审查):
- `LDN I1.1; A I0.3; EU` 提供栈深 1
- `R V300.4, 1` 消耗栈顶 → 栈深 0
- 后续 `R V300.0, 4` / `R V1.6, 1` / `R V1.7, 1` / `FILL 0, VW260, 8` / `R T50, 6` / `MOVW 0, VW2` / `MOVW 0, VW6` / `R V0.0, 1` / `R Q0.7, 1` / `JMP 2`
- **只有第一个 R V300.4, 1 执行**——后续所有 R/MOVW **栈空,不执行!**

**后果**:
- **V300.4 已清 ✓**(第一个 R 执行了)
- **V300.0~3 未清**——下次启动如果还有漫溢报警,会重新触发
- **V1.6/V1.7 未清**——上下缸状态保留(可能误判)
- **VB260-275 未清**——阀门诊断子状态保留(影响后续判断)
- **VW2=0/VW6=0/R V0.0/R Q0.7 都未执行**——**系统无法回 S0!**

**这是一个真正的 P0 致命 BUG**——FC19 的复位链栈消耗导致只有第一条 R 执行,系统永远卡在 S_ERROR 状态!

## 四、验证实验:用真实路径推演

### 4.1 场景 A:实验正常结束,进入 S7

```
[实验 S6 排水完成] 
  → FC17 L69: MOVW 8, VW2            // VW2=8 (进入 S7)
  → FC1 下周期分发: CALL FC18
  → FC18 NETWORK 1: 安全停机(R Q0.0~6,31075.6)
  → FC18 NETWORK 2: 不监听 I0.3,只描述
  → FC18 L35-47: 等待 LDN I1.1; A I0.3; EU
  → 操作员释放急停 + 按 I0.3
  → 条件满足: 清 M10.6,清 V1.0,清 VD364/440/372,VW2=0
  → FC1 下周期分发: CALL FC10 (S0)
  → ✅ 正常回 S0,流程正确
```

**风险**:FC18 L39-47 也是栈消耗链,需要复核:
```stl
LDN   I1.1
A     I0.3
EU
R    M10.6, 1
R    V1.0, 1
MOVR 0.0, VD364
MOVR 0.0, VD440
MOVR 0.0, VD372
MOVW 0, VW2
```
- `EU` 后栈深 1
- `R M10.6, 1` 消耗栈顶 → 栈深 0
- 后续 R/MOVR/MOVW **栈空,不执行**!
- **M10.6 已清 ✓,但 V1.0/VD364/440/372/VW2 都未清!**
- **S7 永远卡住,流程无法回 S0!**

**这与 FC19 的栈消耗问题完全一样**——两个 FC 都有相同的致命 BUG!

### 4.2 场景 B:急停触发,进入 S_ERROR

```
[急停按钮触发]
  → FC2 L24-29: I1.1↑ → S V300.4 → MOVW 99, VW2
  → FC1 下周期分发: CALL FC19
  → FC19 NETWORK 1: 安全停机(QB0=0, S Q0.7)
  → FC19 NETWORK 2: 检查 V300.5
  → FC19 NETWORK 3: 等待 LDN I1.1; A I0.3; EU
  → 操作员: ① 释放急停 → I1.1=OFF;② 按 I0.3
  → 条件满足: 清 V300.4, 清 V300.0~3, 清 V1.6/V1.7, 清 VB260-275, 清 T50~55, VW2=0, VW6=0, 清 V0.0, 清 Q0.7
  → FC1 下周期分发: CALL FC10 (S0)
  → ✅ 正常回 S0,流程正确
```

**风险**:**与 FC18 一样的栈消耗问题**(见 4.1)——只有第一条 R 执行,后续不执行。

### 4.3 场景 C:急停触发 → I1.1 没释放,直接按 I0.3

```
[急停触发 → VW2=99, V300.4=1]
  → 操作员:**没有释放急停,直接按 I0.3**
  → FC19 NETWORK 3: 条件 LDN I1.1; A I0.3; EU
  → I1.1=ON(急停仍触发) → LDN I1.1=FALSE → A I0.3 不满足 → EU 不触发
  → **FC19 复位动作不执行**
  → 系统仍卡在 S_ERROR,VW2=99
  → ✅ 路径正确(按 §9.3 严格顺序执行)
```

### 4.4 场景 D:S7 状态下,FC19 自动解锁触发

```
[实验结束进入 S7,VW2=8]
  → FC18 LDN I1.1; A I0.3; EU 不满足
  → 突然报警触发(其他 FC): MOVW 99, VW2
  → FC19 NETWORK 4: 自动解锁条件检查(假设 VW6=0 等)——如果满足,自动回 S0
  → ✅ 自动回 S0,FC18 没机会执行复位
```

## 六、🔴 关键发现:FC18 和 FC19 都存在栈消耗致命 BUG

### 6.1 FC18 (S7 复位) 栈消耗失效

**文件**:`plc/stl/FC18_State_S7_End.stl` L35-47

**代码**:
```stl
LDN   I1.1                        // 栈深 1
A     I0.3                        // 栈深 1
EU                                // 栈深 1(边沿检测)
R    M10.6, 1                     // 消耗栈顶 → 栈深 0
R    V1.0, 1                      // 栈空,不执行 ⚠️
MOVR 0.0, VD364                   // 栈空,不执行 ⚠️
MOVR 0.0, VD440                   // 栈空,不执行 ⚠️
MOVR 0.0, VD372                   // 栈空,不执行 ⚠️
MOVW 0, VW2                       // 栈空,不执行 ⚠️
```

**实际行为**:
- M10.6 已清 ✓
- V1.0 未清 ✗
- VD364/440/372 未清 ✗
- VW2 未改(仍=8)✗ —— **S7 永远卡住**

### 6.2 FC19 (S_ERROR 复位) 栈消耗失效

**文件**:`plc/stl/FC19_State_Error.stl` L45-67

**代码**:
```stl
LDN   I1.1                        // 栈深 1
A     I0.3                        // 栈深 1
EU                                // 栈深 1
R    V300.4, 1                    // 消耗栈顶 → 栈深 0
R    V300.0, 4                    // 栈空,不执行 ⚠️
R    V1.6, 1                      // 栈空,不执行 ⚠️
R    V1.7, 1                      // 栈空,不执行 ⚠️
FILL 0, VW260, 8                  // 栈空,不执行 ⚠️
R    T50, 6                       // 栈空,不执行 ⚠️
MOVW 0, VW2                       // 栈空,不执行 ⚠️
MOVW 0, VW6                       // 栈空,不执行 ⚠️
R    V0.0, 1                      // 栈空,不执行 ⚠️
R    Q0.7, 1                      // 栈空,不执行 ⚠️
JMP  2                            // 栈空,JMP 不执行(?)
```

**实际行为**:
- V300.4 已清 ✓(急停锁存清除)
- V300.0~3 未清 ✗(漫溢级报警残留)
- V1.6/V1.7 未清 ✗(上下缸状态保留)
- VB260-275 未清 ✗(阀门诊断子状态残留)
- T50-T55 未清 ✗(阀门诊断计时器残留)
- VW2 未改(仍=99)✗ —— **S_ERROR 永远卡住**
- VW6 未清 ✗(报警码保留,HMI 仍显示报警)
- V0.0 未清 ✗(启动命令残留,**下一周期自动重启!**)
- Q0.7 未清 ✗(报警声音持续)

### 6.3 这个 BUG 的严重性

**🔴 这是 P0 致命 BUG**——按 I0.3 后:
- **V300.4 被清(V300.4 是 FC2 NETWORK1 检测急停触发的前提条件),但 VW2 没变回 0**
- 下一周期 FC1 仍分发到 FC19——但 V300.4=0,FC2 不会再次强制 VW2=99
- **如果 VW2 没变回 0,系统永远卡在 S_ERROR(显示 VW2=99)**
- 实际后果:**用户按 I0.3 后看起来"急停好像清了",但系统实际仍处于故障锁定状态,必须 PLC 断电重启**

## 七、修复建议

### 7.1 FC18 修复方案

**用中间位 + 多个 LD 模式**:

```stl
// FC18 L35-47 修复
LDN   I1.1
A     I0.3
EU
=     M_Temp_SysReset              // 中间位保存触发条件

LD    M_Temp_SysReset
R     M10.6, 1

LD    M_Temp_SysReset
R     V1.0, 1

LD    M_Temp_SysReset
MOVR  0.0, VD364

LD    M_Temp_SysReset
MOVR  0.0, VD440

LD    M_Temp_SysReset
MOVR  0.0, VD372

LD    M_Temp_SysReset
MOVW  0, VW2

R     M_Temp_SysReset, 1           // 清理中间位
```

### 7.2 FC19 修复方案

```stl
// FC19 L45-67 修复
LDN   I1.1
A     I0.3
EU
=     M_Temp_SysReset              // 中间位保存触发条件

LD    M_Temp_SysReset
R     V300.4, 1

LD    M_Temp_SysReset
R     V300.0, 4

LD    M_Temp_SysReset
R     V1.6, 1

LD    M_Temp_SysReset
R     V1.7, 1

LD    M_Temp_SysReset
FILL  0, VW260, 8

LD    M_Temp_SysReset
R     T50, 6

LD    M_Temp_SysReset
MOVW  0, VW2

LD    M_Temp_SysReset
MOVW  0, VW6

LD    M_Temp_SysReset
R     V0.0, 1

LD    M_Temp_SysReset
R     Q0.7, 1

R     M_Temp_SysReset, 1
JMP   2
```

### 7.3 验证修复后的行为

修复后:
- FC18:每个 R/MOVR/MOVW 都有自己的 LD M_Temp_SysReset 提供栈顶,都能执行 ✓
- FC19:每个 R/FILL/MOVW 都执行 ✓
- 系统能正确回 S0 ✓

## 八、综合结论

### 8.1 路径冲突问题

**结论**:I0.3 一个按钮驱动两个流程**不会走错路径**——因为:
1. FC1 通过 VW2 状态分发,**同一周期只可能进入 FC18 或 FC19**
2. FC18/FC19 内部都已做了"先检查状态,再执行动作"的保护
3. JMP/LBL 机制防止重复执行

### 8.2 但存在 P0 致命 BUG

**结论**:**两个 FC 的复位链都存在栈消耗失效问题**——按 I0.3 后只有第一条 R 执行,后续动作全失效,系统**永远无法从 S7 或 S_ERROR 回到 S0**。

**这是最严重的问题**——比"路径冲突"更严重,因为即使路径正确,**目的地也永远到不了**。

### 8.3 优先级建议

| 优先级 | 修复项 | 预估工时 |
|---|---|---|
| 🔴 P0-1 | FC18 栈消耗失效 | 0.5h |
| 🔴 P0-2 | FC19 栈消耗失效 | 0.5h |
| 🟠 P1-1 | FC19 自动解锁路径测试 | 1h |
| 🟡 P2-1 | §4.3/§9.3 设计文档与代码对齐 | 0.5h |

### 8.4 对用户问题的直接回答

> "一个系统复位按钮,实现了两个不同的流程,会不会走错路径?"

**回答**:**不会走错路径**——PLC 通过 VW2 状态自动选择进入 FC18 还是 FC19,同一周期只可能执行其中一个 FC。

**但还有更严重的问题**:**按 I0.3 后,即使走对了 FC,FC18 和 FC19 的复位动作链都存在栈消耗失效 BUG,系统永远卡在 S7 或 S_ERROR,无法回到 S0**。
