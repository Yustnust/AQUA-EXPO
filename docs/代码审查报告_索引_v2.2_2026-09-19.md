## ⚠️ 关于修订的诚实声明

**本次审查过程中,我对 S7-200 SMART STL 指令的栈行为有过系统性误判**。

**误判内容**:
- 误以为 `MOVx 立即数/字地址, OUT` 会消耗栈顶
- 误以为 `MOVx AC0, OUT` 会消耗栈

**实际情况**(经西门子官方文档确认):
- `MOVx IN, OUT` 当 IN 是立即数或字地址时,**不消耗栈**,无条件执行
- 只有 `S bit, N` / `R bit, N` / `= bit` / `AENO` / 间接寻址 才消耗栈

**修订影响**:
- 原报告 "79 个 BUG" 是过度评估
- 修订后:**6 P0 + 8 P1 + 12 P2 真正确认**
- 所有"架构/接口/责任划分"类 BUG 仍然有效(不依赖栈分析)

**关于方法论的反思**:
- 直接从 STL 文本追踪每条指令的栈深度是**复杂且容易出错**的
- 更可靠的方法是用 STEP 7-Micro/WIN SMART 的 STL 状态监视功能实际运行程序
- 建议团队在 STEP 7 中下载并单步调试,确认本审查的真实 BUG

## 📝 关于本次审查的方法论

### 审查过程

1. **审查前**:建立对 STL 指令集的理解,但有偏差
2. **审查中**:逐文件读 STL,识别"看似有问题"的代码
3. **审查后**:发现错误,通过查阅西门子官方文档纠正理解

### 学到的教训

1. **MOV 类指令不消耗栈**(IN 是立即数/字地址时)
2. **TON/CTU/CALL 看栈顶使能但不消耗栈**
3. **栈消耗 BUG 触发的关键模式**:`LD + S/R/=/AENO + 后续 S/R/MOVW(无 LD)`
4. **网络间的栈是独立的**(每个 NETWORK 开始栈深=0)
5. **跨 SBR/CALL 的栈是隔离的**

### 推荐工具

- STEP 7-Micro/WIN SMART STL 状态监视(可实时查看栈深)
- 灰度表示指令未执行——这是确认栈消耗 BUG 的最可靠方法
- 单步调试 LD + S + S 模式可验证栈空问题
