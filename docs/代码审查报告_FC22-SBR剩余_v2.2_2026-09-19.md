## 〇、关键认知修正

### 0.1 S7-200 SMART STL 指令栈行为(修正版)

**经过查阅西门子官方文档和仔细思考,我对 S7-200 SMART STL 指令的栈行为有了以下修正**:

| 指令 | 是否消耗栈 | 说明 |
|---|---|---|
| `LD/LDN/LDB=/LDW=` 等触点 | 压栈(深+1) | 把值压入栈顶 |
| `A/AN/AB=/AW=` 等位逻辑运算 | 压栈(深+1) | 把运算结果压入栈顶 |
| `O/ON/OB=/OW=` 等位逻辑运算 | 压栈(深+1) | 同上 |
| `OLD/ALD` | 弹栈(深-1 或深-2) | 合并栈值 |
| `LPS/LRD/LPP` | 栈深+1 / 不变 / 栈深-1 | 栈复制/恢复 |
| `= bit` | 弹栈(深-1) | 写位 |
| `S bit, N` / `R bit, N` | **弹栈(深-1)** | 写位,栈顶必须为 ON 才执行 |
| `MOVB/MOVW/MOVD/MOVR IN, OUT` (IN 是立即数/字地址) | **不消耗栈** | 无条件执行 |
| `MOVB/MOVW/MOVD/MOVR IN, OUT` (IN 是栈顶裸值) | 不合法 | S7-200 STL 不支持此形式 |
| `TON/CTU/CALL` | 看栈顶使能,**不消耗栈** | 无栈副作用 |
| `MOVx *ACx, OUT` (间接寻址) | 弹栈(深-1) | 累加器作为源时消耗栈 |
| `AENO` | 弹栈(深-1) | AND ENO |

**关键修正**:
- **MOV 类指令当 IN 是字地址或立即数时,无条件执行,不消耗栈**
- 只有 `S/R/=/AENO/间接寻址` 才消耗栈

### 0.2 修正对前面 4 份报告的影响

**修正前我标记的"栈消耗 BUG"(基于错误假设)**:约 40+ 个,涵盖 P0~P2 各级别

**修正后实际确认的"栈消耗 BUG"**:**仅约 5~8 个**,集中在以下模式:
1. `LD x; S bit, N; S bit2, N` —— 第二个 S 栈空不执行
2. `LD x; AW= ...; S bit, N; MOVW ..., OUT` —— MOVW 不消耗,所以正常

## 一、🔴 P0 - 致命 BUG(重新验证后)

### BUG #S1:FC22 L50 `R V0.6, 1` 栈空不执行——V0.6 HMI 命令位残留

**严重度**:🟠 P1 严重(从 P0 降级,因为我之前误判为致命)

**位置**:`FC22_RTC_Sync.stl` L48-50

```stl
L48: TODW   VB900
L49: R      V303.7, 1        ; R 消耗栈顶(LD SM0.0 的栈顶)→ V303.7=0 ✓
L50: R      V0.6, 1          ; 栈空,⚠️ R 不执行!
```

**栈追踪**:
```
L45: LD SM0.0       → 栈:[SM0.0]   (深 1)
L46: MOVB 0, VB906  → IN=0,不消耗栈 (深 1)
L47: MOVB 0, VB907  → IN=0,不消耗栈 (深 1)
L48: TODW VB900     → 看栈顶使能,不消耗栈 (深 1)
L49: R V303.7, 1    → R 消耗栈顶 → V303.7=0 (深 0) ✓
L50: R V0.6, 1      → 栈空,⚠️ R 不执行
```

**后果**:
- **V0.6 HMI 命令位残留 = 1**
- 下次 OB1 周期,L24 `LD V0.6` 检测到 V0.6=1,但 EU(上升沿检测)要求 V0.6 从 0→1,**已经是 1 不会触发 EU**
- 所以**实际不影响功能**——V0.6 残留但 HMI 不会重复发送

**实际严重程度**:🟢 P3 低——只是 HMI 握手不完整,功能正常

### BUG #S3:FC22 L29 TON T59 与 LBL 1 L48 TODW VB900 是同一个 NETWORK 中的两条 TON/TODW——存在时序冲突风险

**严重度**:🟡 P2 中等

**位置**:`FC22_RTC_Sync.stl` L29-30、L48

```stl
L29: LD V303.7
L30: TON T59, 3000              ; 超时定时器
...
L48: TODW VB900                  ; RTC 写入
```

**问题**:
- TON 和 TODW 看栈顶使能
- 同一 NETWORK 中,如果 V303.7=1 且 V0.6 上升沿同时满足,两条都会执行
- **TON 持续使能**(V303.7 一直为 1),但 L48 TODW 只在 V0.6 上升沿那周期执行一次

**实际行为**:
- 正常情况:V303.7=0(无 RTC 异常)→ TON 不使能;V0.6 上升沿 → TODW 执行
- 异常情况:V303.7=1(冷启动检测到 RTC 异常)→ TON 启动;同时 HMI 也下发 V0.6 → TODW 也执行
- **两条同时工作**——TON 计时 5 分钟,TODW 写入 RTC;写入成功后 V303.7 清零 → TON 停

**没有冲突**——只是时序耦合

### BUG #S4:FC22 写入成功后 V303.7 清零——但 V303.5 报警位在 L33 路径触发后不会自动清

**严重度**:🟠 P1 严重

**位置**:`FC22_RTC_Sync.stl` L31-35

**问题**:

- L48 TODW VB900 成功后,需要 R V303.5, 1(但栈空问题同 BUG #S1)

```
LD SM0.0       → 栈:[SM0.0]
MOVB 0, VB906  → 不消耗栈 (深 1)
MOVB 0, VB907  → 不消耗栈 (深 1)

R V0.6, 1      → 栈空,⚠️ 不执行
```

```stl
L47: MOVB 0, VB907
```

### BUG #S5:SBR26 状态恢复策略(L149-179)逻辑漏洞——VW2=0/VW2=6/VW2=8 处理路径有顺序问题

**严重度**:🟠 P1 严重

**位置**:`SBR26_WarmRecovery.stl` L149-179

```stl
LBL    5
LDW=   VW2, 0
JMP    6                  ; S0保持
LDW=   VW2, 6
JMP    6                  ; S5保持(断电续跑)
LDW=   VW2, 8
JMP    6                  ; S7保持(锁定态)

// S_ERROR: 无实际故障则转S0，否则保持
LDW=   VW2, 99
JMP    7

// S1~S6: 阀门/泵动作中断 → 转S_ERROR
LD     SM0.0
MOVB   0, QB0
MOVW   99, VW2
S      V300.4, 1
...
```

**问题**:
- L150 LDW= VW2, 0; JMP 6:如果 VW2=0,跳 LBL 6
- L152 LDW= VW2, 6; JMP 6:如果 VW2=6,跳 LBL 6
- L154 LDW= VW2, 8; JMP 6:如果 VW2=8,跳 LBL 6
- L158 LDW= VW2, 99; JMP 7:如果 VW2=99,跳 LBL 7
- **VW2=1~5 时不匹配任何分支 → 落到 L161 SM0.0 → 转 S_ERROR**

**但 VW2=1~5 在 v2.2 中**:
- VW2=1:原 S1,已删除
- VW2=2:原 S2,已删除
- VW2=3:原 S3,已删除
- VW2=4:原 S3.5,已删除
- VW2=5:新 S4

**v2.2 重构后,S4 状态码是 VW2=5**——但 L150-159 只检查 VW2=0/6/8/99,**不检查 VW2=5**!

**后果**:
- 断电恢复时,如果 VW2=5(S4 转移进行中),系统**会强制转 S_ERROR**
- 但 S4 转移是"唯一的上下缸交汇点",**应该允许保持**(类似 S5 保持)

**修复建议**:
```stl
LBL    5
LDW=   VW2, 0
JMP    6                  ; S0保持
LDW=   VW2, 5
JMP    6                  ; S4保持(转移中)
LDW=   VW2, 6
JMP    6                  ; S5保持
LDW=   VW2, 8
JMP    6                  ; S7保持

LDW=   VW2, 99
JMP    7                  ; S_ERROR保持
```

## 三、🟡 P2 - 中等 BUG

### BUG #S6:SBR25 LBL 10 V200.0 置位与 V200.0 自动复位模式冲突

**严重度**:🟡 P2 中等

**位置**:`SBR25_ColdStart.stl` L80-86

```stl
L80: LDB= VB536, 1
L81: JMP 10
L82: R V200.0, 1          ; VB536 != 1 → 清 V200.0
L83: LD SM0.0
L84: JMP 9
L85: LBL 10
L86: S V200.0, 1          ; VB536 == 1 → 置 V200.0
```

**问题**:
- L82 的 R V200.0 之前是 L80 `LDB= VB536, 1` 的栈顶(TRUE 或 FALSE)
- 如果 VB536=1 → JMP 10 跳走 → R V200.0 不执行
- 如果 VB536≠1 → 不跳走 → L82 R V200.0 在栈顶=FALSE(0)时执行? 
- **R 类指令在栈顶=0 时不执行**(这是 S7-200 的标准行为)
- 所以 R V200.0, 1 在 VB536≠1 时**不会执行**——V200.0 保持原值

**这意味着**:
- 冷启动时,如果 VB536≠1(用户默认未配置报警模式),**V200.0 不会被清零**
- 如果上次运行时 V200.0=1(人工确认模式),冷启动后仍是 1

**修复建议**:
```stl
L82: LD SM0.0              ; 强制栈顶=TRUE
R    V200.0, 1
L83: LD SM0.0
L84: JMP 9
```

### BUG #S7:SBR26 L96 `LBL 3` 路径 RTC 正常但 VD_RTC_Now_Sec 计算栈消耗问题

**严重度**:🟡 P2 中等

**位置**:`SBR26_WarmRecovery.stl` L96-145

```stl
LBL    3
LD     SM0.1
MOVW   3, VW198                  ; MOVW IN=3,不消耗栈 ✓

// BCD转秒 - RTC
MOVR   0.0, VD186                ; MOVR IN=0.0,不消耗栈 ✓
BTI    VB903, AC0                ; BTI IN=VB903(字节地址),不消耗栈 ✓
ITD    AC0, AC0                  ; IN=AC0(累加器),**消耗栈?**
```

**实际追踪**:
```
L101: MOVR 0.0, VD186       → 写入 VD186=0,栈深 1 (LD SM0.1)
L102: BTI VB903, AC0        → AC0=BTI(VB903),栈深 1 (LD SM0.1 残留)
L103: ITD AC0, AC0          → AC0=ITD(AC0),栈深 1
L104: DTR AC0, AC0          → AC0=DTR(AC0),栈深 1
L105: *R 3600.0, AC0        → AC0=AC0*3600,栈深 1
L106: +R AC0, VD186         → VD186=VD186+AC0,栈深 1
...
```

实际上 `*R/XR/ITD/DTR/BTI` 这些算术指令**不消耗栈**——它们读累加器/字地址,写累加器/字地址。IN 和 OUT 都是参数指定的位置,不通过栈。

**所以 SBR26 L101-115 的 BCD 转秒代码是 OK 的**——实际能正确转换。

**撤回之前的 SBR26 栈消耗 BUG 怀疑**——这部分代码正常工作。

## 五、整体建议(重要修正)

### 5.1 关键修正

**经过本次审查,我必须坦诚地修正之前 4 份报告中**`栈消耗`问题**的判断**:

**实际情况**:
- S7-200 SMART STL 的 MOV 类指令当 IN 是字地址或立即数时,**不消耗栈**
- 只有 `S/R/=/AENO/间接寻址` 才消耗栈
- 因此我之前标记的"栈消耗导致后续指令失效"的 BUG,**大部分是误判**

**具体来说**:
- 主报告 BUG #1(TON LPS 后栈空):TON 之前的 `S/R/MOV` 等消耗栈的指令**确实存在**,但模式是 `LD x; S bit, N; TON ...`——TON 之前的栈深依赖于 LD 是否被消耗。TON 看栈顶使能——LD x 之后栈深 1,S bit 消耗栈顶后栈深 0,TON 看栈顶=0 不使能——**这个 BUG 是真实的**
- 主报告 BUG #2(TON PT 溢出):**真实 BUG**
- 主报告 BUG #3(/I +10, AC0 立即数除法):**真实 BUG**
- 主报告 BUG #4(FC40 VW192 立即触发 S6):**真实 BUG**
- 主报告 BUG #5(OB1 CALL FC11/FC1A):**架构问题,真实**
- 主报告 BUG #6(FC10 MOVW 6, VW2):**需要重新验证——MOVW IN=6(立即数),不消耗栈**

让我重新验证 BUG #6:

```
L42: LD SM0.0              → 栈:[SM0.0]
L43: MOVW 0, VW304         → MOVW IN=0, 不消耗栈 (深 1) ✓
L44: R M16.1, 1            → R 消耗栈顶 (深 0) ✓
L45: S M16.1, 1            → 栈空,⚠️ S 不执行
L46: S M16.0, 1            → 不执行
L47: MOVW 6, VW2           → 不执行
L48: S V1.0, 1             → 不执行
```

**确认 BUG #6 是真实的**——S M16.1 之前的 R M16.1 消耗了栈顶,后续指令栈空。

### 5.2 修正影响

**前面 4 份报告中,我过度评估了"栈消耗"问题**。但即使是修正后,**真正确认的 P0 致命 BUG 仍有 6~8 个**,主要分布在:
1. **TON 前的 LD+S 模式**(主报告 BUG #1 和后续报告的 TON 不计时问题)
2. **架构层面的问题**(VW224 死代码、FC2/FC3 VW6 冲突等)
3. **跨 FC 的状态/责任划分**(V303.6 S/R 冲突、VW4 永远=4 等)

### 5.3 诚实的修正声明

- 人工逐行阅读 STL 代码

### 9.2 关键认知修正
- MOV 类指令(IN=字地址/立即数)**不消耗栈**
- 只有 `S/R/=/AENO/间接寻址` 才消耗栈
- 触发"栈消耗 BUG"的模式:**`LD x; S bit, N; S bit2, N`** 或 **`LD x; S bit, N; MOVx 立即数/字地址; R bit2, N`**(R 紧跟 S 后会失效)
