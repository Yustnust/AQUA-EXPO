# 药液配置加注控制系统 — 变更管理流程 v1.0

**项目**: AQUA-EXPO 药液配置与加注控制系统
**适用范围**: 8台S7-200 SMART PLC(STL代码20个FC)+ HMI + 全部交付文档
**变更管理工具**: Jira(缺陷跟踪)+ GitHub(代码变更PR)+ 变更单(本流程核心)
**版本**: v1.0
**日期**: 2026-07-18
**配套文档**: PLC程序版本管理规范v1.0、代码评审checklist v1.0、项目交付文档总索引v1.0

## 第1章 变更分类

### 1.1 变更类型

| 类型 | 编码前缀 | 定义 | 典型场景 | 审批权限 |
|---|---|---|---|---|
| 需求变更(新功能) | AQEX-CHG-R | 新增功能/扩展能力,对应Story迭代 | 新增FC/新增报警位/新增HMI画面 | 项目负责人 |
| 缺陷修复 | AQEX-CHG-B | 修复校验报告/静态分析/现场反馈的缺陷 | VW270冲突修复/MOVB误用修复 | L2维护(一般)/L3管理员(严重) |
| 优化重构 | AQEX-CHG-O | 不改变功能,优化代码结构/性能/可维护性 | 编址区迁移/FC拆分/算法优化 | L3管理员 |
| 文档变更 | AQEX-CHG-D | 仅文档变更,不涉及代码 | 规格书修订/SOP更新/手册补充 | 文档负责人 |
| 参数调整 | AQEX-CHG-P | HMI设定参数默认值/通讯参数/超时值调整 | VD48超时值调整/Modbus波特率变更 | L2维护(默认值)/L3管理员(通讯) |
| 紧急变更 | AQEX-CHG-E | 现场紧急缺陷修复,走快速通道 | 急停失效/通讯中断/无法启动 | L3管理员(口头先行) |

### 1.2 各类审批权限矩阵

| 变更类型 | 申请人 | 评估人 | 审批人 | 实施人 | 测试人 | 发布人 |
|---|---|---|---|---|---|---|
| 需求变更(R) | 项目经理/客户 | PLC工程师 | 项目负责人 | PLC工程师 | 调试工程师 | L3管理员 |
| 缺陷修复-一般(B) | 调试工程师/L2 | PLC工程师 | L2维护 | PLC工程师 | 调试工程师 | L2维护 |
| 缺陷修复-严重(B) | 任意发现人 | PLC工程师+调试工程师 | L3管理员 | PLC工程师 | 调试工程师 | L3管理员 |
| 优化重构(O) | PLC工程师 | PLC工程师+HMI工程师 | L3管理员 | PLC工程师 | 调试工程师 | L3管理员 |
| 文档变更(D) | 任意角色 | 文档负责人 | 文档负责人 | 文档编写人 | (评审人) | 文档负责人 |
| 参数调整-默认值(P) | 调试工程师 | PLC工程师 | L2维护 | PLC工程师 | 调试工程师 | L2维护 |
| 参数调整-通讯(P) | 调试工程师 | PLC工程师+网络工程师 | L3管理员 | PLC工程师 | 调试工程师 | L3管理员 |
| 紧急变更(E) | 现场工程师 | L3管理员(口头) | L3管理员(口头) | 现场工程师 | 现场工程师 | L3管理员 |

### 1.3 变更分级

| 等级 | 判定条件 | 审批要求 |
|---|---|---|
| L1(轻微) | 仅注释订正/文档错别字/不影响功能 | 评审人1名 |
| L2(一般) | 单FC修改/不影响编址/不影响安全功能 | L2维护审批 |
| L3(重要) | 多FC修改/影响编址/影响变量表/影响HMI | L3管理员审批 |
| L4(重大) | 状态机变更/编址区迁移/8台PLC拓扑变化/通讯协议切换/安全功能变更 | 项目负责人+公司技术负责人双签 |

## 第2章 变更走单流程

### 2.1 标准流程

```
[1.变更申请]    [2.影响评估]    [3.审批]    [4.实施]    [5.测试]    [6.发布]    [7.归档]
   ↓               ↓              ↓           ↓           ↓           ↓           ↓
  申请人          评估人        审批人       实施人       测试人       发布人      配置管理
  创建变更单     填评估表       分级签字     代码修改     回归测试     8台同步     单据归档
  填申请模板     识别影响       (L1~L4)     PR+评审      SAT/FAT      下装+验证   知识库更新
                                              checklist   用例         标签+CHANGELOG
```

### 2.2 流程步骤详解

#### 步骤1: 变更申请

**申请人**创建《变更单》(Jira issue 类型=Change,或独立文档),填写以下模板:

```
==========================================
变更单 AQEX-CHG-<R/B/O/D/P/E>-<NNN>
==========================================
变更类型: □需求变更R □缺陷修复B □优化重构O □文档变更D □参数调整P □紧急变更E
变更等级: □L1轻微 □L2一般 □L3重要 □L4重大
关联Jira: AQEX-<NNN>(如缺陷单/Story单)
申请人: __________ 申请日期: YYYY-MM-DD

变更描述:
<2~5句话清楚描述要做什么变更>

变更原因:
<为什么要变更?缺陷症状?需求来源?优化目标?>

影响范围:
- PLC代码: □OB1 □FC0 □FC1~FC4 □FC10~FC19 □FC30~FC40 □无
- HMI组态: □画面1~8 □变量表 □无
- 变量地址表: □新增地址 □修改地址 □删除地址 □无
- 文档: □规格书 □校验报告 □SOP □手册 □无
- 8台PLC一致性: □影响(需同步下装) □不影响
- 安全功能: □影响 □不影响

涉及文件:
- plc/stl/FC11_State_S1_Inlet.stl (修改: VD48运算逻辑)
- plc/stl/FC0_SysInit.stl (修改: NETWORK0 版本号登记)
- docs/HMI-PLC变量地址表_v1.0.md (修改: 9.2报警码同步)
- ...

回滚方案:
- 回滚目标版本: vX.Y.Z
- 回滚方式: □Git revert □重新下装旧版.mwp □参数恢复CSV
- 回滚审批人: __________

预计工时: ___人时
预计完成: YYYY-MM-DD
```

#### 步骤2: 影响评估

**评估人**(由变更类型决定,见1.2节)填写《影响评估表》(详见第3章):

```
==========================================
影响评估表
==========================================
评估人: __________ 评估日期: YYYY-MM-DD
关联变更单: AQEX-CHG-<R/B/O/D/P/E>-<NNN>

评估维度:
- PLC逻辑影响: □无 □单FC □多FC □状态机 □安全联锁
  影响说明: ____________________
- HMI组态影响: □无 □变量增减 □画面调整 □权限调整
  影响说明: ____________________
- 变量地址影响: □无 □新增 □修改 □删除 □编址区迁移
  影响说明: ____________________
- 文档影响: □无 □规格书 □校验报告 □SOP □手册
  影响说明: ____________________
- 8台PLC一致性: □不影响 □影响(8台同步下装)
  影响说明: ____________________
- 安全功能影响: □无 □急停 □联锁 □报警 □断电恢复
  影响说明: ____________________

风险评估:
- 风险等级: □低 □中 □高
- 风险点: ____________________
- 缓解措施: ____________________

回归测试范围:
- □校验报告v1.0全部检查项
- □静态分析(0严重/0警告目标)
- □SAT/FAT相关用例(用例编号: ___)
- □8台PLC同步验证
- □HMI验证
- □现场验收

评估结论: □可实施 □需修改后重评 □不可实施
```

#### 步骤3: 审批

**审批人**根据变更等级(1.3节)签字:

| 变更等级 | 审批人 | 审批时限 | 审批方式 |
|---|---|---|---|
| L1轻微 | 评审人1名 | 1工作日 | GitHub PR Approve |
| L2一般 | L2维护 | 2工作日 | 变更单签字 |
| L3重要 | L3管理员 | 3工作日 | 变更单签字 |
| L4重大 | 项目负责人 + 公司技术负责人 | 5工作日 | 评审会议 + 双签 |

**审批意见模板**:
```
审批意见: □同意 □有条件同意(条件:___) □不同意(原因:___)
审批人签字: __________ 日期: __________
```

#### 步骤4: 实施

**实施人**按以下步骤执行:

1. 创建分支(见PLC程序版本管理规范第2章):
   - 需求变更: `feature-<scope>-<story>-<desc>`
   - 缺陷修复: `fix-<scope>-<issue>-<desc>`
   - 紧急变更: `hotfix-<scope>-<issue>-<desc>`
2. 修改代码/文档,遵循提交规范(见版本管理规范第3章)
3. 提交PR到 develop(或 hotfix 到 main)
4. PR评审(见代码评审checklist v1.0)
5. 评审通过后合并

**实施记录**:
```
实施人: __________ 实施日期: YYYY-MM-DD
PR链接: https://github.com/.../pull/NNN
合并commit: <hash>
实际涉及文件:
- <文件1>
- <文件2>
实施过程说明: ____________________
```

#### 步骤5: 测试

**测试人**按影响评估表的回归测试范围执行:

1. 静态分析: `python tools/stl_static_analyzer.py`,目标 0 严重
2. 完整性校验: 对照校验报告v1.0检查项
3. 单元测试: 修改FC的功能测试
4. 集成测试: 跨FC调用链测试
5. SAT/FAT用例: 101个用例中相关用例回归
6. 8台PLC同步验证(仅发布前)
7. HMI验证(仅涉及HMI变更)

**测试记录**:
```
测试人: __________ 测试日期: YYYY-MM-DD
测试范围: ____________________
测试结果: □通过 □部分通过(失败用例:___) □不通过
测试报告: <附件或链接>
发现问题: ____________________
```

#### 步骤6: 发布

**发布人**按以下步骤发布:

1. 创建 release-x.y 分支(见版本管理规范第2章)
2. 填写版本号到 FC0 NETWORK0 (VW0)
3. 更新 CHANGELOG.md(见版本管理规范第7章)
4. 执行发布检查清单(见版本管理规范第4.3节)
5. 合并到 main 并打标签 vX.Y.Z
6. 8台PLC同步下装(见版本管理规范第5章)
7. 下装后验证(见版本管理规范第6.5节)

**发布记录**:
```
发布人: __________ 发布日期: YYYY-MM-DD
发布版本: vX.Y.Z
标签: vX.Y.Z
8台PLC下装记录:
- PLC#1 (192.168.2.101): 下装时间___ 操作人___ 状态□
- PLC#2 (192.168.2.102): 下装时间___ 操作人___ 状态□
- ... (8台全部)
版本一致性验证: □8台一致 □不一致(处置:___)
```

#### 步骤7: 归档

**配置管理工程师**归档:

1. 变更单关闭(Jira状态→Closed)
2. 变更单PDF存档至 `docs/achieve/change/<变更单号>.pdf`
3. 评审记录存档至 `docs/achieve/review/<变更单号>/`
4. 测试报告存档至 `docs/achieve/test/<变更单号>/`
5. 发布记录存档至 `docs/achieve/release/<版本号>.md`
6. 更新项目交付文档总索引(如新增文档)
7. 更新知识库(如本次变更有经验教训)

## 第3章 影响评估

### 3.1 评估维度

变更影响评估必须从以下6个维度全面分析:

#### 维度1: PLC逻辑影响

| 子项 | 评估内容 |
|---|---|
| 影响FC数量 | □1个 □2~5个 □6~10个 □>10个 |
| 影响FC类型 | □OB1 □FC0初始化 □FC1调度 □FC2急停 □FC3报警 □FC4通讯 □FC10~FC19状态 □FC30~FC32诊断 □FC40纠偏 |
| 状态机变更 | □不变 □新增状态 □修改状态转移 □删除状态 |
| 调用链变更 | □不变 □新增调用 □修改调用顺序 □删除调用 |
| 算法变更 | □不变 □差值法/纠偏算法/报警优先级链 等 |

#### 维度2: HMI组态影响

| 子项 | 评估内容 |
|---|---|
| 变量增减 | □不变 □新增变量 □修改变量 □删除变量 |
| 画面调整 | □不变 □画面1总览 □画面2详情 □画面3手动 □画面4参数 □画面5报警 □画面6趋势 □画面7通讯 □画面8系统 |
| 权限调整 | □不变 □L1操作员权限 □L2维护权限 □L3管理员权限 |
| 报警组态 | □不变 □新增报警位 □修改报警位含义 □删除报警位 |

#### 维度3: 变量地址影响

| 子项 | 评估内容 |
|---|---|
| 地址变更 | □不变 □新增地址 □修改地址含义 □删除地址 □编址区整体迁移 |
| 影响地址区 | □V0/V1命令状态位 □VW2~VW8 □VD10~VD66参数 □VD70~VD102实测 □VD104~VD140纠偏 □VW200~VW228 Modbus □VW230~VW289诊断 □VB300~VB303报警字 □DT10时间戳 |

#### 维度4: 文档影响

| 子项 | 评估内容 |

| SOP/手册 | □不变 □现场调试SOP □操作手册 □维护手册 |
| 评审checklist | □不变 □需补充检查项 |

#### 维度5: 8台PLC一致性影响

|---|---|

|---|---|

| 阀门联锁 | □不变 □影响 |
| 漫溢保护 | □不变 □影响 |

## 第4章 紧急变更流程

### 4.1 适用场景

紧急变更适用于现场紧急缺陷,符合以下条件之一:

| 场景 | 示例 |
|---|---|
| 安全功能失效 | 急停按钮无响应/安全继电器反馈异常/阀门联锁失效 |
| 8台PLC无法运行 | 状态机卡死/无法进入S0/通讯中断导致HMI不可控 |
| 工艺中断且无规避 | 加药计量错误/排水超时/实验数据丢失 |
| 现场验收阻塞 | SAT/FAT关键用例失败阻塞验收 |

### 4.2 紧急流程

```
现场紧急缺陷
    ↓
口头/电话申请 → L3管理员口头审批(立即)
    ↓
现场工程师 hotfix 分支修改 → 现场测试(简化) → 直接下装到故障PLC
    ↓
    ├── 单台故障: 单台下装(见版本管理规范5.4)
    └── 多台故障: 8台紧急同步下装
    ↓
PLC恢复运行
    ↓
24小时内补登变更单 AQEX-CHG-E-NNN
    ↓
补办评审(代码评审checklist v1.0)+ 补办完整测试
    ↓
评审通过 → 合并到 main + develop → 打标签 vX.Y.Z
    ↓
归档(同标准流程步骤7)
```

### 4.3 限制条件

紧急变更有以下限制:

| 限制项 | 要求 |
|---|---|
| 范围限制 | 仅修复紧急缺陷本身,不得借机夹带其他变更 |
| 文档后补 | 文档变更可后补,但代码变更必须现场评审 |
| 测试简化 | 现场可仅做关键功能测试,但24小时内必须补全回归测试 |
| 审批记录 | L3管理员口头审批必须有书面记录(微信/邮件/电话会议纪要) |
| 24小时补单 | 24小时内必须补登完整变更单,否则视为违规 |
| 一致性恢复 | 单台紧急回滚后,7天内必须决策: ①补下装最新版 ②保持回滚至下个发布 |
| 复盘 | 紧急变更完成后7天内召开复盘会议,分析根因+预防措施 |
| 频次限制 | 单月紧急变更≤2次,超出需公司技术负责人介入 |

### 4.4 紧急变更单模板(简化版)

```

<2~3句话描述缺陷现象+影响>
```

## 第5章 变更与Jira联动

### 5.1 Jira issue 类型与变更单关联

| Jira issue 类型 | 用途 | 与变更单关系 |
|---|---|---|
| Story | 新功能需求(对应Story1.2~1.7等) | 1个Story → 1或多个变更单 AQEX-CHG-R |
| Bug | 缺陷跟踪 | 1个Bug → 1个变更单 AQEX-CHG-B |
| Epic | 大型需求集合 | 1个Epic → 多个Story → 多个变更单 |
| Task | 任务(非代码) | 通常不产生变更单 |
| Change | 变更单(本项目自定义) | 直接对应 AQEX-CHG-* |

### 5.2 缺陷修复变更关联缺陷单

缺陷修复变更必须关联Jira缺陷单:

```
Jira Bug AQEX-101 (FC32 MOVB写字地址)
    ↓ (关联)
变更单 AQEX-CHG-B-015 (FC32 MOVB→MOVW修复)
    ↓ (实施)
GitHub PR #45 (fix-fc32-AQEX-101-movb-misuse)
    ↓ (合并)
commit f49496c (fix(plc): 修复校验报告发现的2严重+4警告问题)
    ↓ (发布)
Tag v1.0.1 (CHANGELOG: Fixed - FC32 L138/L159 MOVB 1,VW270 改为 MOVW 1,VW270)
```

### 5.3 状态同步规则

| Jira Bug状态 | 变更单状态 | 说明 |
|---|---|---|
| Open | — | 缺陷已登记,未启动修复 |
| In Progress | 申请中/评估中 | 创建变更单,开始流程 |
| In Review | 实施中/测试中 | PR评审中或测试中 |
| Resolved | 发布中 | 测试通过,准备发布 |
| Closed | 归档 | 发布完成,Jira关闭 |

### 5.4 Jira字段同步

Jira Bug/Change issue 必须填写的字段:

| 字段 | 内容 |
|---|---|
| Summary | 简述 |
| Description | 详细描述(对应变更单"变更描述") |
| Priority | 缺陷优先级(对应变更等级L1~L4) |
| Assignee | 责任人(对应实施人) |
| Reporter | 报告人(对应申请人) |
| Issue Links | 关联其他issue(Story/Epic/PR) |
| Fix Version | 修复版本(对应发布版本 vX.Y.Z) |
| Resolution | 解决方案(对应变更单"实施记录") |
| Components | 影响组件(FC11/HMI/变量表 等) |
| Labels | 标签(如"静态分析"/"校验报告"/"紧急") |

### 5.5 Git提交与Jira关联

Git提交信息必须包含Jira issue号(见版本管理规范3.4节):

```
fix(plc): 修复FC32 VW270跨FC写入冲突

校验报告v1.0 P2: VW270被FC30用作T50 PT值,被FC32用作诊断结果。
本提交将FC30 T50/T51 PT值迁移至VW278/VW280,与FC32诊断结果VW270隔离。

关联: AQEX-CHG-B-015, AQEX-101
回归: 校验报告v1.0 P2, 静态分析跨FC写入冲突#29
```

GitHub PR描述必须包含:
- 关联变更单号 AQEX-CHG-XXX
- 关联Jira issue号 AQEX-NNN
- 关联校验报告/静态分析问题编号
- 回归测试结果

### 6.4 追溯链

任何一次发布,必须能完整追溯:

```
发布版本 vX.Y.Z
    ↑ 标签
Git commit (合并release-x.y到main)
    ↑ PR
GitHub PR (release-x.y → main)
    ↑ 评审记录
代码评审checklist(填写版)
    ↑ 修复提交
多个 feature-*/fix-* 分支提交
    ↑ 关联
多个变更单 AQEX-CHG-XXX
    ↑ 关联
多个Jira issue (Bug/Story)
    ↑ 关联
校验报告问题编号(如P2/P5/A1)
静态分析问题编号(如#3/#29)
```

**追溯能力要求**: 给定一个现场PLC版本号(如v1.0.2),应能在30分钟内回答:
- 该版本包含哪些变更单?
- 每个变更单的申请人/审批人/实施人?
- 每个变更单的根因(关联的Jira issue/校验问题)?
- 该版本的8台PLC下装时间/操作人?
- 该版本与前一个版本的差异(CHANGELOG)?
