## 〇、关于本次修订

### 0.1 修订原因

之前提交的 4 份审查报告中,**我对 S7-200 SMART STL 指令的栈行为存在系统性误判**:

| 误判 | 实际情况 |
|---|---|
| `MOVx IN, OUT`(IN=立即数/字地址)消耗栈 | **不消耗栈,无条件执行** |
| `MOVx AC0, OUT`(累加器作为源)消耗栈 | **不消耗栈**(AC0 不在栈上) |
| 大量"栈消耗 P0/P1 BUG" | **大部分是误判** |

### 0.2 真正确认的栈消耗触发模式

只有以下形式才会触发"栈消耗导致后续指令失效"问题:

```stl
// 模式 A:连续 S/R/= 链
LD   x
S    bit, 1     ; 消耗栈顶
S    bit2, 1    ; 栈空,不执行! ⚠️
R    bit3, 1    ; 不执行

// 模式 B:TON 前的 S/R
LD   x
S    bit, 1     ; 消耗栈顶
TON  Txx, PTV   ; 栈空,FALSE,TON 不使能 ⚠️

// 模式 C:= 指令后跟 S
LD   x= bit1     ; 消耗栈顶
S    bit2, 1     ; 栈空,不执行! ⚠️
```

### 0.3 修订后真实情况

- **真正确认的 P0 致命 BUG**:6 个(从原报告的 17 个降下来)
- **真正确认的 P1 严重 BUG**:8 个
- **真正确认的 P2 中等 BUG**:约 12 个
- **真正确认的 P3 低优先级**:若干

### P0 #2:FC4 VW224→VW4 状态归一化是死代码——VW4 永远=4

**文件**:`FC4_ModbusPolling.stl`
**位置**:L78-89
**状态**:✅ 已确认(无需栈分析)
**确认方法**:
- VW224 在整个 FC4 中**从未被 MBUS_MSG 写入**(L26 写入的是 `&VB410`,不是 `&VB224`)
- VW224 永远是 0
- 归一化逻辑:`AW<> VW224, 100; AW<> VW224, 96; AW<> VW224, 64` —— VW224=0 满足所有条件
- `MOVW 4, VW4` 执行 → **VW4 永远=4(归一化错误码)**

**后果**:
- 所有依赖 VW4 状态的逻辑(FC13/FC21 全局错误检测、运动中判定)全部失效
- FC13 子状态机无法进入"等抽液运动完成"等需要"VW4≠运动中"的逻辑
- FC13/FC21 全局错误检测 `AW>= VW4, 4` 永远为 TRUE → **VW390 永远被设为 99**
- **VW4=0(就绪)永远检测不到**——FC21 子状态机写命令永远不发

**修复**:删除 L78-89 整个归一化段,直接使用 L59 的 `MOVW VW410, VW4`

### P0 #5:TON PT 16 位 INT 溢出——冷启动即报警 V303.6

**文件**:`FC11_State_S1_Inlet.stl` L54-62 + `FC40_RhythmCorrection.stl` L80-81、L103-105
**状态**:✅ 已确认(无栈相关)
**确认方法**:
- 默认 VD414=24 → T_single = 3600s
- T_cycle = 3600 - 30 - 10 = 3560s
- `T_cycle×10 = 35600`,**超过 INT 上限 32767**
- `MOVW AC0, VW286` 写入 16 位 INT,溢出为负数
- **TON T46/T48 立即 Done**——PV=32767 或 0
- FC40 的 `AW<= VW192, 0` 立即为 TRUE
- **FC40 每周期都触发"参数过激进"路径**,S V303.6=1,转 S_ERROR

**后果**:**冷启动即报警 V303.6,系统永远 S_ERROR**

**修复**:
- 改用 32 位定时器(S7-200 SMART 不支持)
- 拆分多个 100ms TON 串接
- 改用 1s 时基
- 减少乘法因子

### P0 #6:`/I +10, AC0` 立即数除法——S7-200 SMART 编译器直接报错

**文件**:`FC40_RhythmCorrection.stl` L143、L147
**状态**:✅ 已确认
**确认方法**:
- S7-200 SMART 的 `/I IN1, OUT` 指令要求 **IN1 必须是字地址**,不支持立即数
- `+10` 这种立即数形式在 STL 里是非法的
- STEP7 编译会失败

**修复**:
```stl
MOVW +10, VWxxx    ; 先把立即数放进 VW
/I   VWxxx, AC0    ; 再除
```

### P1 #2:FC40 首轮/空计时器状态下 VW192 立即触发 S6

**文件**:`FC40_RhythmCorrection.stl` L84-93
**位置**:L84-93、L107-117
**确认方法**:
- `MOVW VW190, VW192` → IN=VW190,不消耗栈
- `-I VW194, VW192` → 看栈顶,栈空,FALSE,**-I 不执行!**
- 即使 `-I` 执行:VW192 = 0 - S6_actual*10 = 负数
- `AW<= VW192, 0` → 栈深 1,执行(VW192 是负数)
- L88 LPS + L89-90 ALD + MOVW 7, VW2 → **VW2=7,S6 转移触发**

**实际行为**:即使 `-I` 不执行,栈深 1 跳到 L88,LPS 把它保存,L89 LDW= VW2, 6 → 栈深 2(LPS 之前是 1,LPS 后 2),L90 AW= VW6, 0 → 栈深 2,LPP 弹出,栈深 1,ALD 合并,LPS 弹出,栈深 0,MOVW 7, VW2 消耗栈顶(MOVW IN=7,不消耗栈,但栈深 0,MOVW 也不执行)——**VW2 不变成 7**

但**TON 在 L62 是 VW190 = T46/TPV** — 任何周期都检查 PV<=S6_actual,如果 TON 真的能计时,这个判断不会立即满足——但 **TON 之前已经被 PT 溢出问题搞坏**(P0 #5)

**修复**:在比较条件上加 `A T46` 或 `A T48`(计时器正在计时才比较)

## 四、被误判的 BUG 清单(应从 P0/P1 移除)

### 误判 #1:FC11 NETWORK 1 L30-41 的 TON T37 链栈消耗

**原判断**:P0 致命——所有 TON 不使能
**修正后判断**:**部分误判**
- `MOVR VD358, VD332; *R 10.0, VD332; ROUND VD332, AC0; MOVW AC0, VW278` —— 这些 MOV/R 类指令的 IN 是字地址/累加器,**不消耗栈**
- 栈深实际上保持在 1,TON T37 看栈顶=TRUE,**TON 使能成功** ✓

---

### 误判 #2:FC40 NETWORK 1 L43-47 `AR> VD186, 0.0; JMP 10; LD SM0.0; S V303.6, 1; JMP 9` 链栈消耗

**原判断**:P0 致命
**修正后判断**:**误判**——`S V303.6, 1` 之前的栈深是 1(LD SM0.0 之后),S 消耗栈顶后栈深 0,但 `S` 执行成功,**V303.6 仍被置位**——只是后续 JMP 9 跳走(LBL 9 是 NETWORK 结束,自动清栈)

---

### 误判 #3:FC40 NETWORK 1 L51-57 `MOVR VD186, VD190; *R 10.0, VD190` 链栈消耗

**原判断**:P0 致命
**修正后判断**:**误判**——MOVR IN=VD186(字地址)、*R IN=10.0(立即数)都不消耗栈

---

### 误判 #4:FC17 S6 排水路径 `MOVB 1, VB264; MOVB 0, VB265; MOVW 0, VW270` 等

**原判断**:P0/P1——栈空不执行
**修正后判断**:**部分误判**——这些 MOV 指令的 IN 是立即数,不消耗栈。但**TON T42 之前是 R T42, 1 消耗栈顶,TON 看栈顶=FALSE,不使能**——这是真实的栈 BUG,见 P1 #6

---

### 误判 #5:FC3 报警码优先级链 MOVW 短路逻辑

**原判断**:P0/P1——MOVW 依赖栈顶 FALSE 不执行
**修正后判断**:**误判**——MOVW IN=10/11/.../99 是立即数,不消耗栈。栈顶=FALSE 时 MOVW 不执行是 S7-200 标准行为,但 MOVW 不消耗栈是确认的——**这条本身工作正常**
