# AQUA-EXPO PLC 代码审查报告（v2.2 分支）

> **审查日期**：2026-09-19
> **审查人**：PLC 代码审查助手
> **审查对象**：`feature/v2.2-doc-revisions` 分支（commit `26702ba8`，2026-09-18 13:32 UTC）
> **审查范围**：`plc/stl/` 下 27 个 STL 文件（约 4000 行）+ `docs/S2-S4流程重构设计方案_v2.2.md`
> **整体结论**：⚠️ **代码存在多处严重缺陷，核心 STL 栈管理错误会导致系统无法启动或完全停摆。建议在合并到 master 前必须重写，或至少有资深 PLC 工程师现场把关。**

---

## 〇、摘要

| 严重度 | 数量 | 主要影响 |
|---|---|---|
| 🔴 **P0 致命** | 6 个 | 系统上电即停摆、流程完全卡死 |
| 🟠 **P1 严重** | 5 个 | 部分功能失效（计时、S4/S6 完成动作、加药初始化） |
| 🟡 **P2 中等** | 7 个 | 影响功能正确性、可维护性 |
| 🟢 **P3 低** | 5 个 | 规范、可维护性、文档一致性 |

**根因总结**：

1. **P0 几乎全部源自同一个根因——STL 栈管理错误**：LPS 后用 `MOVB/MOVW/MOVR/S/R` 这些栈消耗指令，导致后续指令（尤其 `TON`）在栈空时不执行。S7-200 SMART 的栈深只有 8 层，任何稍微复杂的逻辑都需要明确每条指令的栈深变化。
2. **P1 严重 bug 大多是 P0 的衍生**：`TON` 不计时 → 计时类操作全部失效 → 状态转移、阀操作、Modbus 写等都失效。
3. **`TON` PT 16 位 INT 溢出**是独立的设计缺陷，与 STL 栈管理无关，但与 v2.2 的"双倒计时器"算法强耦合。
4. **设计文档 §5.x 给出的 STL 伪代码本身有错**（`/I +10, ...`、`MOVW T46, VW190` 在 LD 后没保留栈），说明设计阶段**没有经过 STEP7 编译验证**，这一点最致命。

## 一、🔴 P0 - 致命 BUG（系统无法运行）

### BUG #1：`TON` 定时器在 LPS 后栈被耗空，定时器从未使能

**严重度**：🔴 P0 致命
**影响范围**：几乎所有计时类功能

**位置**：
- `FC40_RhythmCorrection.stl` L62-63（虽然此处没直接 `TON`，但 `MOVW T46, VW190` 在 `LD M16.0` 后用栈空，间接影响后续）
- `FC11_State_S1_Inlet.stl` L50-62：启动 `T46/T48`（双倒计时器）
- `FC1A_State_S2_MixDose.stl` L24-36：启动 `T38`（S2 搅拌）
- `FC15_State_S4_Transfer.stl` L29（启动 `T49`）、L57-58（启动 `T61`）
- `FC17_State_S6_Drain.stl` L19（启动 `T42`）
- `FC16_State_S5_Run.stl` L23（LPS 后 `TON T60`）、L36（`TON T47`）

**问题代码模式**：
```stl
LD   条件1            ; 栈深 1
LPS                   ; 栈深 2
S    Q0.x, 1          ; 消耗栈顶，栈深 1
R    Txx, 1           ; 消耗栈顶，栈深 0
TON  Txx, +xxx        ; ⚠️ 栈空！TON 看栈顶=FALSE，TON 不使能
MOVB 1, VBxxx         ; 栈空，不执行！
MOVW ..., VWxxx       ; 栈空，不执行！
LPP                   ; 栈深 1
```

**原理**：S7-200 SMART 的 STL 里，`TON/CALL/比较指令`等的 IN（使能）看栈顶，栈顶是 FALSE/0 时指令不执行。`LPS` 后只有 2 层栈，下面用 4~6 个 `S/R/MOV` 立刻把栈吃光，`TON` 实际上永远得不到 TRUE。

**后果**：
- `T38`（S2 搅拌）永远不计时 → 上缸 S2 永远卡死，无法转 `VW304=3`
- `T42`（S6 排水）永远不计时 → S6 完成判定失效，`FC40` S6 触发条件也失效
- `T46/T48`（双倒计时器）永远不计时 → `FC40` S6/下一轮 S1 触发条件永远满足（因为 PV=0）→ 系统会**进入一个死循环**：每周期都尝试转 S6，但 S6 也卡住
- `T60`（下缸满秒计时）、`T47`（实验分钟累加）同样失效
- **整个系统上电后无法推进任何流程**

**修复建议**：每个 `TON` 单独一行 NETWORK，确保 `LD` 后立即接 `TON`；或者用 `LD` 链保持栈顶。

### BUG #2：`TON` PT 16 位 INT 溢出

**严重度**：🔴 P0 致命
**影响范围**：所有计时器的 PT 值

**位置**：
- `FC11_State_S1_Inlet.stl` L54-62：`MOVR VD186, VD190; *R 10.0, VD190; ROUND; MOVW AC0, VW286/VW288; TON T46/T48`
- `FC1A_State_S2_MixDose.stl` L32-36：同模式
- `FC40_RhythmCorrection.stl` L80-81（`VW194 = S6_actual × 10`）、L103-105（`VW200`）
- `FC15_State_S4_Transfer.stl` L53-56（T61）、L29（T49）

**问题**：
- S7-200 SMART `TON` 的 PT 是 **16 位 INT**，范围 **0~32767**
- 默认 `VD414=24` → `T_single = 86400/24 = 3600s` → `T_cycle = 3600 - 30 - 10 = 3560s` → `T_cycle×10 = 35600` **溢出 INT**
- 即使换算时用 `ROUND` 放入 AC0（VW），**`MOVW AC0, VW286` 时 35600 会被截到 16 位**，变成负数或 0
- `T46/T48` **立即 Done**——PV=32767 或 0，`FC40` 的 `AW<= VW192, 0` **立即为 TRUE**

**触发连带**：参见 BUG #4。

**修复**：
- 把所有计时器 PT 改用 32 位或拆分为多个 100ms 计时器
- 或采用"时分秒"三个 `TON` 串接
- 或减少乘法因子（如改用 1s 时基而非 100ms）

### BUG #3：`/I +10, AC0` 立即数除法 - S7-200 SMART 编译器直接报错

**严重度**：🔴 P0 致命
**影响范围**：`FC40` 显示值计算；文档示例代码

**位置**：
- `FC40_RhythmCorrection.stl` L143、L147：
  ```stl
  MOVW T46, AC0
  /I   +10, AC0      ; ⚠️ S7-200 SMART 不支持立即数除法
  ITD  AC0, VD256
  ```
- `docs/S2-S4流程重构设计方案_v2.2.md` §5.4 L387：`/I +10, VD186`（文档里也错了）

**问题**：
- S7-200 SMART 的 `/I IN1, OUT` 指令要求 **IN1 必须是字地址**（VW/VD/AC/常量），**不支持立即数**
- 即 `+10` 这种立即数形式在 STL 里是非法的，STEP7 会**编译失败**
- 这是设计文档里的伪代码错误，直接被复制到了 STL

**修复**：
```stl
MOVW +10, VWxxx    ; 把立即数先放进 VW
/I   VWxxx, AC0    ; 再除
```
或：
```stl
MOVW 10, AC0
/I   AC0, ...      ; 不行，IN1 和 OUT 不能相同
```

### BUG #4：首轮/空计时器状态下 VW192 立即触发 S6

**严重度**：🔴 P0 致命
**影响范围**：系统启动后第一个周期

**位置**：`FC40_RhythmCorrection.stl` L84-93、L107-117

**问题代码**：
```stl
MOVW VW190, VW192     ; VW192 = T46/T48 当前 PV
-I   VW194, VW192     ; VW192 = PV - S6_actual*10
AW<= VW192, 0         ; PV <= S6_actual*10 ?
```

- 当 `T46/T48` **未启动**时，PV=0，`VW192 = 0 - S6_actual*10` = **负数**
- `AW<= 负数, 0` = TRUE → **每周期都触发 S6 转移**（只要 `VW2=6` 且 `VW6=0`）

**实际表现**：
- 首轮 `FC10` 触发 `VW2=6`（S5 空等）后（假设 BUG #16 也修了），`FC40` 第一周期就检测到 PV=0 ≤ S6_actual，**直接 `MOVW 7, VW2`** 转 S6
- S6 触发后阀 C 不开（参见 BUG #8），下缸水排不出去，系统卡死

**修复**：在 `AW<=` 条件上加 `A T46` 或 `A T48`（计时器**正在计时**才比较），确保计时器已启动才参与比较。

### BUG #5：OB1 NETWORK 11 CALL FC11/FC1A 调度错误

**严重度**：🔴 P0 致命
**影响范围**：上缸子流程调度

**位置**：`OB1_MAIN.stl` L116-121

```stl
LD   SM0.0
AW=  VW304, 1
CALL State_S1_Inlet
LD   SM0.0
AW=  VW304, 2
CALL State_S2_MixDose
```

**问题**：
- STL 里 **CALL 指令不依赖栈顶 TRUE/FALSE**（不像 LAD 里的 EN 输入），CALL **总是执行**
- `AW= VW304, 1` 的结果被压在栈里，但 **CALL 不消耗栈顶**
- 后续 `LD SM0.0; AW= ...; CALL` 持续压栈，会导致 **栈深逐渐累积**

**实际表现**：
- 即使 `VW304=0`（空闲），**`FC11_State_S1_Inlet` 和 `FC1A_State_S2_MixDose` 也会每周期被调用**
- `FC11` 内部用 `M10.2`（S1 首次进入标志）控制，但 FC1 的 S1 入口 `S M10.2, 1`（L69）只在 `VW2=1` 时执行；`VW2=6`（S5 空等）时 `M10.2` 不会被置 1，FC11 内部就**什么也不做**
- 但 FC11 里的 `AW= VW260, 0` 判断在 `VW304=0` 时仍然进行（因为 CALL 不看栈），执行空转——没实际副作用
- **真正的风险是栈累积**：每周期 `LD SM0.0; AW=...; CALL; LD SM0.0; AW=...; CALL;` 后栈深大约 3~4 层（取决于 CALL 是否真的消耗栈），长期运行**不会**栈溢出，但**资源浪费 + 时序错乱**

**修复**：
- 用 `MCR/JMP` 或 LAD 块
- 或者让 `FC11/FC1A` 内部首句 `LDW= VW304, 1; NOT; RET`

---

### BUG #6：`FC10` 首轮启动 `MOVW 6, VW2` 不执行

**严重度**：🔴 P0 致命
**影响范围**：系统启动

**位置**：`FC10_State_S0_Init.stl` L42-52

```stl
LD   SM0.0
MOVW 0, VW304
R    M16.1, 1
S    M16.1, 1
S    M16.0, 1
MOVW 6, VW2          ; ⚠️ 这里之前已经被前面的 S/R 把栈吃空了
S    V1.0, 1
```

**问题**：
- 上一段 LPS 后 `AW= VW6, 0; A I0.6; NOT; JMP 1` 用了 1 个栈值，然后 JMP 跳到此处继续
- `LD SM0.0` 提供 1 个栈值给 `MOVW 0, VW304`
- 然后 `R/S/MOVW/S` 共 4 个消耗栈指令，**`MOVW 6, VW2` 是第 5 个，栈已经空了！**
- **`VW2` 永远不变成 6**，下缸永远停在 S0（初始化态），系统无法启动

**修复**：每条独立 NETWORK；或把每个 `MOVW/S` 用 `LD SM0.0` 起头。

## 二、🟠 P1 - 严重 BUG（部分功能失效）

### BUG #7：`FC17` LPS 后所有 S4 完成动作全部失效

**严重度**：🟠 P1 严重
**影响范围**：S6 完成判定、S6→S4 转移、计数、计时器切换

**位置**：`FC17_State_S6_Drain.stl` L37-49（阀 C 诊断结果分支）、L83-83（M16.0 切换）

**问题**：
- 与 BUG #1 同模式：LPS 后所有 `MOVB/MOVW/S` 栈消耗殆尽
- `VB270`（阀 C 诊断结果）检查后，后续 `R T42, 1; MOVW T42, AC0; ITD; DTR; MOVR; ...` 全部栈空不执行
- **`VD116` 永远不更新**（S6 实测时长丢失）
- **S6→S4 的状态转移不执行**（`MOVW 5, VW2`）、**`VW306` 不递增**（`INCW VW306` 不执行）、**`M16.0` 不切**（`NOT M16.0, = M16.0` 不执行）
- **系统一旦进 S6，永远不会退出**，除非 OB1 停止命令

**修复**：参见 BUG #1。

### BUG #8：`FC17` LPS 后阀 C 从未打开 + VB264 不初始化

**严重度**：🟠 P1 严重
**影响范围**：S6 排水流程

**位置**：`FC17_State_S6_Drain.stl` L13-28

**问题**：
```stl
LD   M10.7
EU
LPS
S    Q0.4, 1          ; 消耗栈顶，栈深 1
R    T42, 1           ; 消耗栈顶，栈深 0
TON  T42, 32767       ; ⚠️ 栈空，TON 不使能
MOVB 1, VB264         ; 栈空，不执行！
MOVB 0, VB265
MOVW 0, VW270
...
LPP
```

- LPS 后只有 1 个栈值可用，下面 7+ 个 S/MOV 消耗指令
- **`Q0.4` 阀 C 不开** → **下缸永远排不出去水**
- `VB264` 不初始化为 1（等待开到位），`FC32` 诊断逻辑错乱
- 即使 `Q0.4` 开了，`TON T42` 也不计时

**修复**：参见 BUG #1。

### BUG #9：`FC13` 加药流程 LPS 后整个初始化失效

**严重度**：🟠 P1 严重
**影响范围**：S3 加药流程

**位置**：`FC13_State_S3_Dosing.stl` L52-72（S3 进入/子状态 0）

**问题**：
```stl
LD   SM0.0
AW=  VW226, 0
LPS
MOVR VD584, VD372    ; 消耗栈顶，栈深 0
S    Q0.0, 1          ; 栈空，不执行！
S    Q0.1, 1          ; 栈空
R    M12.0, 1         ; 栈空
R    M12.1, 1
R    M12.2, 1
R    M11.6, 1
R    M11.7, 1
R    T102, 1
```

- 加药子状态机永远停在 0 → **注射泵永远不启动** → 加药流程完全失效

### BUG #10：`FC15` S4 完成动作全部失效

**严重度**：🟠 P1 严重
**影响范围**：S4 转移完成、计时器切换、双状态机同步

**位置**：`FC15_State_S4_Transfer.stl` L85-126

**问题**：
```stl
LD   SM0.0
LPS
AB=  VB268, 1          ; 消耗栈顶，栈深 1
LPP                    ; 栈深 1
NOT                    ; 栈深 1
JMP  10                ; 栈深 1（假设 JMP 不跳）
R    T49, 1            ; 消耗栈顶，栈深 0
MOVW T49, AC0          ; ⚠️ 栈空，不执行！
ITD  AC0, VD444        ; 栈空
DTR  VD444, VD444      ; 栈空
MOVR VD444, VD116      ; 栈空 → VD116 不更新
S    V1.7, 1           ; 栈空 → 下缸永远不显示"满"
...
MOVW 6, VW2            ; 栈空 → S4→S5 不转移
```

**后果**：
- **`VD116` 不写入 S4 实测时长**（`FC40` S6 触发阈值失效）
- **`V1.7` 不置位**（下缸永远不显示"满"，后续状态转移卡住）
- **`DT10` 不写入**（下缸变满时间戳丢失，实验计时失效）
- **`M16.0` 不切**（双计时器失效）
- **`MOVW 6, VW2` 不执行**（S4→S5 不转移）
- **S4 永远不会完成**

**修复**：参见 BUG #1。

### BUG #11：`FC15` S4 实测时长单位错误（100ms 而非秒）

**严重度**：🟠 P1 严重
**影响范围**：FC40 S6 触发阈值

**位置**：`FC15_State_S4_Transfer.stl` L93-97

```stl
MOVW T49, AC0         ; AC0 = T49 当前 PV（100ms 时基）
ITD  AC0, VD444       ; → DINT
DTR  VD444, VD444     ; → REAL
MOVR VD444, VD116     ; VD116 = T49 PV（100ms 时基，⚠️ 应为秒）
```

**问题**：
- 设计意图是存**秒**，但实际 `VD116` 存的是**100ms 时基的原始计数**
- `VD116` 比实际秒数大 **10 倍**
- 后续 `FC40` 计算 `S6_actual = VD116; ×10`，变成 `T49_100ms × 10 × 10 = T49_100ms × 100` 倍
- S6 触发条件 `PV ≤ S6_actual×10` **永远不成立**（阈值被放大 100 倍）
- 设计文档 §5.4 写的是 `/I +10, VD186`（又错了——立即数除法 + 应该 IN2 不是 IN1），实际代码改成 ITD/DTR 又**忘了除 10**

**修复**：
```stl
MOVW T49, AC0         ; AC0 = T49 当前 PV（100ms 时基）
/I   VW_Ten, AC0      ; 先除 10 转秒
ITD  AC0, VD444
DTR  VD444, VD444
MOVR VD444, VD116
```
或在 `SBR25` 里初始化 `VW_Ten = 10`。

## 三、🟡 P2 - 中等 BUG（影响功能/可维护性）

### BUG #12：`VW8` 计算公式与文档不一致

**严重度**：🟡 P2 中等
**影响范围**：HMI 显示

**位置**：`OB1_MAIN.stl` L186-191 + 文件头注释 L19

```stl
MOVR VD414, AC0       ; VD414 = 24h 换水目标次数
*R   VD24, AC0        ; VD24 = 实验目标总时长（min）
/R   1440.0, AC0      ; 1440 min/day
ROUND AC0, AC0
DTI   AC0, VW8        ; VW8 = 实验全程应完成的总换水次数
```

**问题**：
- 注释写的是"实验总换水次数目标"，**公式是 `(24h_目标次数 × 实验总时长min) / 1440min`** —— 这个其实是"按 24h 换水次数折算的总实验时长内的换水次数"
- 但设计文档 §4.6 写的是 `VW306 >= VD414`，**只看 24h 目标，不乘以实验时长**——OB1 里算的 VW8 没被任何地方使用，可能是给 HMI 显示用，但文档没说明。
- 如果 HMI 显示这个 VW8 作为"目标"，会误导操作员以为"实验完成 = VW306 >= VW8"，但实际 S7 触发只看 `VW306 >= VD414`，二者数值差异可能很大。

**修复**：
- 在文档 §4.6 明确说明"VW8 仅作 HMI 显示用，实际判定条件为 `VW306 >= VD414`"
- 或把计算公式改为 `VW8 = VD414`（保持简单）

### BUG #13：VW304 双状态机与 VW2 主状态机的状态机冲突

**严重度**：🟡 P2 中等
**影响范围**：双状态机同步

**位置**：`FC1_StateDispatcher.stl`、`OB1_MAIN.stl` L116-121

**问题**：
- v2.2 把状态机拆成两个：下缸 VW2（主）、上缸 VW304（子）
- OB1 在 FC1 调度 VW2 后，再 `AW= VW304, 1/2` 调 FC11/FC1A
- 但 FC11/FC1A 内部用 `AW= VW260, 0`（阀 A 诊断子状态）作为首次进入门控，**不检查 VW304**
- 如果 `VW304=0`（空闲），但 FC11 仍被 OB1 调用，**FC11 内部的诊断子状态=0 满足，可能误触发 S1 流程**
- 类似 BUG #5 的连锁问题

**修复**：
- FC11/FC1A 入口加 `LDW= VW304, 1; NOT; RET`（FC11）/ `LDW= VW304, 2; NOT; RET`（FC1A）

### BUG #14：V303.6 单轮换水周期超时报警永不自动清除

**严重度**：🟡 P2 中等
**影响范围**：报警系统

**位置**：`FC40_RhythmCorrection.stl` L122-136

**问题**：
- `S V303.6, 1` 一旦置位，**只有 V0.3 人工确认才能清除**（FC3 处理）

**修复**：
- 在 `FC40` 启动时（首周期）增加 "首次扫描不清 V303.6" 的逻辑，避免冷启动后立即误报
- 或在 `FC22`（RTC Sync）确认校时完成后才允许清 V303.6

## 六、根因详细分析

### 6.1 STL 栈管理错误的根本原因

S7-200 SMART 的 STL 栈深度限制为 **8 层**，每条指令对栈的影响如下：

| 指令类型 | 栈影响 | 示例 |
|---|---|---|
| `LD / LDN / LDI / LDNI` | 压栈（+1） | `LD SM0.0` |
| `A / AN / O / ON` | 与栈顶做逻辑运算，结果压栈（+1） | `A I0.0` |
| `=  位地址` | 弹栈（-1），不修改栈顶值 | `= Q0.0` |
| `S / R  位地址, N` | 弹栈（-1） | `S Q0.0, 1` |
| `MOVB / MOVW / MOVR / MOVD` | 弹栈（-1），源在栈顶 | `MOVW 0, VW2` |
| `+R / -R / *R / /R / +I / -I ...` | 弹栈（-1） | `+R AC0, VW2` |
| `LPS` | 复制栈顶到第 2 层（栈深 +1） | `LPS` |
| `LRD` | 复制第 2 层到栈顶（栈深不变） | `LRD` |
| `LPP` | 弹栈（-1），丢弃栈顶，保留第 2 层 | `LPP` |
| `TON / CTU / CALL ...` | 看栈顶作为 IN（使能），但**不消耗栈** | `TON T38, VW252` |

**关键陷阱**：
1. `TON` 看栈顶作为使能，但**不消耗栈**。如果前面所有 `LD` 都被后续的 `MOV/S/R` 消耗光了，`TON` 的栈顶是 0/FALSE，**TON 不使能**。
2. `LPS` 后只有 2 层栈可用，如果后面用 5 个 `MOV/S`，栈早就空了，**最后几个指令全部不执行**。
3. STL 没有"块结束自动弹栈"机制，每条指令的栈深变化必须手动追踪。

### 6.2 设计文档与代码不一致

`docs/S2-S4流程重构设计方案_v2.2.md` §5.x 给出的 STL 伪代码本身有错：
- §5.4 L387：`/I +10, VD186`（立即数除法）
- §4.2 `MOVW T46_PV, VW190`（TON PV 直接读取不能写）
- §5.2 NETWORK X：FC1A 完成判定 `LDW= VW226, 9; A T38; ...` 但实际 v2.2 FC1A 用了 LPS 模式导致栈错乱

**建议**：所有伪代码必须由 PLC 工程师"过编译"再发，文档与代码必须 1:1 对应。

## 七、修复方案示例

### 7.1 BUG #1 修复示例（FC1A_STATE_S2_MixDose）

**原代码**：
```stl
NETWORK 1
LDW=  VW304, 2
AN    M16.3
S     M16.3, 1
LPS
S     Q0.0, 1
S     Q0.1, 1
MOVR  VD28, VD336
*R    10.0, VD336
ROUND VD336, AC0
MOVW  AC0, VW252
TON   T38, VW252      ; ⚠️ 栈空，不使能
MOVW  0, VW226

MOVR  0.0, VD440
LPP
```

**修复后**：
```stl
NETWORK 1
// S2 首次进入门控
LDW=  VW304, 2
AN    M16.3
S     M16.3, 1
=     M16.3_Pulse        ; 用 V 区或 M 区保存脉冲

NETWORK 2
// 开潜水泵
LD    M16.3_Pulse
S     Q0.0, 1
S     Q0.1, 1

NETWORK 3
// 计算 T38 PT
LD    M16.3_Pulse
MOVR  VD28, VD336
*R    10.0, VD336
ROUND VD336, AC0
MOVW  AC0, VW252

NETWORK 4
// 启动 T38
LD    M16.3_Pulse
TON   T38, VW252

NETWORK 5
// 清加药子状态机
LD    M16.3_Pulse
MOVW  0, VW226
R     V303.4, 1
MOVR  VD584, VD372
MOVR  0.0, VD440
```

### 7.2 BUG #2 修复示例（TON PT 16 位 INT 溢出）

**原代码**：
```stl
MOVR VD186, VD190        ; T_cycle = 3560s
*R   10.0, VD190         ; VD190 = 35600（100ms 时基）
ROUND VD190, AC0
MOVW AC0, VW286          ; ⚠️ 35600 溢出 16 位 INT
TON  T46, VW286
```

**修复方案 A（拆分为多个 TON）**：
```stl
// T46 = 分钟计时（PT = T_cycle / 60）
MOVR VD186, VD190
/R   60.0, VD190
ROUND VD190, AC0
MOVW AC0, VW286
TON  T46, VW286          ; PT = 分钟数（最大 60 分钟 = 3600 秒，PT=60，远小于 32767）

// T47 = 秒钟计时（PT = 60）
TON  T47, 6000           ; 60 秒（600×100ms）
```

**修复方案 B（改用 1s 时基）**：
```stl
// 改用 T_SEC 定时器（1s 时基而非 100ms）
MOVR VD186, AC0          ; T_cycle = 3560s
ROUND AC0, VW286         ; PT = 3560，远小于 32767
TON  T46, VW286          ; 1s 时基
```

### 7.3 BUG #3 修复示例（立即数除法）

**原代码**：
```stl
MOVW T46, AC0
/I   +10, AC0            ; ⚠️ 不支持立即数
ITD  AC0, VD256
```

**修复后**：
```stl
// 在 SBR25 初始化时设置 VW_Ten = 10
// （或用任意空闲 VW 区）
MOVW T46, AC0
/I   VW_Ten, AC0
ITD  AC0, VD256
```

## ⚠️ 修订声明(2026-09-19 追加)

**本报告存在"栈消耗 BUG"过度评估的问题**。

编写本报告时,我对 S7-200 SMART STL 指令的栈行为存在系统性误判:
- 误以为 `MOVx 立即数/字地址, OUT` 会消耗栈顶
- 误以为 `MOVx AC0, OUT` 会消耗栈

**实际正确行为**(经西门子官方文档确认):
- `MOVx IN, OUT` 当 IN 是立即数或字地址时,**不消耗栈**,无条件执行
- `MOVx AC0, AC0` 中 AC0 不在栈上,**不消耗栈**
- 只有 `S bit, N` / `R bit, N` / `= bit` / `AENO` / 间接寻址 才消耗栈

**本报告的真实情况**:
- 原报告 P0:6 个 → 修订后**部分确认**,实际只有 ~3 个 P0
- 部分 BUG(如"FC11 NETWORK 1 TON T37 不使能")实际是误判——MOVR/*R/ROUND/MOVW 链的 IN 都是字地址或累加器,不消耗栈
- 真正确认的 P0:#1 TON PT 16 位 INT 溢出、#2 TON LD+S 后 TON 不使能模式(部分)、#3 `/I +10` 立即数除法
- 真正确认的 P0(架构/接口类):#6 FC10 MOVW 6, VW2 链(确认)

**所有"架构/接口/逻辑"类 BUG 仍然有效**——这些不依赖栈分析。
